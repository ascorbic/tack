This file provides guidance to agentic coding tools when working with code in this repository.

## Design principle: delight

The UI must be delightful, with FigJam as the bar: considered typography, micro-interactions, and lots of small details (how a card lifts when picked up, how a live update lands, how a push confirms). Treat polish as a feature, not a follow-up. Respect `prefers-reduced-motion`, and keep interactions at 60fps.

## Repository Structure

Tack: a GitHub-native collaborative whiteboard for open source planning, built as a Cloudflare Worker with Vite+ and the Cloudflare Vite plugin.

- `src/index.ts` — the Worker entrypoint: webhook route, partyserver routing, DO exports
- `src/server/board.ts` — `Board` Durable Object (one per board): Yjs document via y-partyserver, live card relay via custom messages, filtered per connection so private cards only reach viewers who can read them (`visibility.ts`), and watching its repositories while anyone's connected
- `src/server/repo.ts` — `Repo` Durable Object (one per repository, keyed by its id): card cache, board subscriptions, webhook log and fan-out, debounced CI refetches, reconcile on wake, repository status (`live`, `writable`, `visibility`), and ETag polling of repositories without the app while a board has them open (see `docs/github-data.md`)
- `src/server/routing.ts` — maps repository names to `Repo` objects by stable repository id, so renames don't split caches (see `docs/github-data.md`)
- `src/server/instance.ts` — `Instance` Durable Object (a singleton, `instance(env)`): the GitHub App's credentials, installations and their tokens, users, sessions and the access allowlist. Every credential is encrypted at rest with `TACK_SECRET`
- `src/server/directory.ts` — `Directory` Durable Object (a singleton, `directory(env)`): the board index. Boards (id, slug, title, owner, visibility, archived), members by GitHub login, visits ("Recent") and each board's thumbnail sketch. Separate from `Instance` so board traffic (a thumbnail update on every board save) stays off the session-lookup path
- `src/server/boards/` — board access (`access.ts`: `roleFor`, the one function deciding owner/editor/viewer from visibility and membership), the `/api/boards` routes and the per-board check on live connections (`routes.ts`), and thumbnail sketches (`thumbnail.ts`)
- `src/server/identity.ts` — the identity contract other code uses: `getViewer(request, env)` (HTTP and WebSocket upgrades), `viewerToken(env, viewer)` and `canUseInstance(env, viewer)`
- `src/server/auth/` — sign-in and sessions: `/auth/*` and `/api/me` routes (`routes.ts`), the GitHub OAuth flow with PKCE and refresh (`oauth.ts`), signed session cookies (`session.ts`), instance access checks (`access.ts`), and HKDF/AES-GCM/HMAC helpers (`crypto.ts`)
- `src/server/github/` — the GitHub App: manifest and RS256 app JWTs (`app.ts`), `/setup/*` and `/api/setup*` routes (`setup.ts`), webhook verification and installation events (`webhooks.ts`), and the token contract (`tokens.ts`: `repoToken`, `isInstalled`, `appJwt`) that everything reading GitHub goes through, plus the cron that redelivers failed webhooks (`redeliver.ts`)
- `src/server/forges/` — forge adapters (GitHub, plus a synthetic `fake.tack` forge for tests and stress boards): fetching items, verifying and normalising webhooks, capabilities, and writing (`apply`, `canWrite`, `repoMeta`, `listDirectory`; GitHub's are in `github-write.ts`), and reading for widgets (`search`, `related`, `release`; GitHub's search is in `github-search.ts`: GraphQL's `search` with a token, so results are full cards that say whether their repository is private, and anonymous REST issue search without one; once GitHub rate limits a token, that isolate stops searching with it until GitHub says). Everything outside this folder is forge-neutral. `apply` never throws for forge errors: they come back as results, rate limits retryable with `retryAt`, and `ApplyOptions.retryOf` makes creates look for what an unanswered earlier attempt made before making it again. The fake forge's writes succeed without a network (anything with `[fail]` in it is refused), sub-issues and blocked-by included, and its repositories count as writable without any app, so the whole push flow can be tried locally without GitHub. Items it creates are numbered from 100000 (even for issues, odd for pull requests), and their cards are open items of that kind
- `src/server/push/` — pushing staged changes (M2): the routes (`routes.ts`: `POST /api/boards/:id/push`, `GET /api/boards/:id/pushes`, `GET /api/repos/meta`, `GET /api/repos/files`), planning a push (`plan.ts`: checking operations from the document, dependency order, summaries), and the engine each `Board` runs (`engine.ts`). The engine snapshots what was pushed in the board's SQLite storage, applies it one write at a time from the board's alarm (a second apart, in batches, waiting out rate limits in order), writes statuses into the document with `PUSH_ORIGIN` (never undoable), confirms `sent` changes when the card shows them (`reflects` in `src/shared/confirm.ts`; the board subscribes to those items), reconciles ones that don't confirm in time, runs change effects (`replace`: shapes become the created item's card, in place; `place`: a card for the created item above the shapes it came from, connected to them, as a section's parent issue gets, `placeCard` in `src/shared/place.ts`, which slides it clear of other shapes as Expand related does), and keeps the audit log. SQLite is the truth: a change being pushed or applied is never pushed again, whatever the document says
- `src/server/related.ts` — `GET /api/boards/:id/related?key=…` (M3, #42): what's related to an item (parent, sub-issues, blocked-by, blocking, linked pull requests; `related` on the forge adapter, in `github-related.ts` for GitHub along with `release`), for anyone who can open the board, as they may see it: asked with their own token, and anything from a repository that isn't public that they can't read is left out entirely, keys and all
- `src/server/rules.ts` — the rules engine (#44): each `Board` runs its rules (`src/shared/rules.ts`) on every webhook delivery it hears about (`Board.repoActivity`, called by `Repo` for every board subscribed to any of its items, or watching it for an inbox, with the delivery's items under each board's keys and what a pull request's text mentions or closes, `Delivery.mentions`). Rules run with the app's access (the delivery's data) and only place items from repositories already on the board; they write with `RULE_ORIGIN` (never undoable), and which items each rule has placed is kept in the board's SQLite (`rule_placed`), so a rule never places an item twice, even after someone removes it. The same pass keeps "no longer matches" marks (`unmatched`, see `provenance.ts`) current for cards an inbox or a matching rule brought, from the delivery's data (`refreshMatches`); an inbox's results only ever clear marks (`confirmMatches`), since one viewer's results leaving a card out may just mean they can't read it
- `src/server/widgets/runner.ts` — the widget runner (#37), one per `Board`: it runs the queries of every widget (`widgetQueries` from the registry) and inbox section (one query named `inbox`, #40) that a connection watches (`widget-watch`/`widget-unwatch`/`widget-refresh` with shape ids; `inbox-preview` for an inbox editor's live count, answered under `previewId(section)`), and sends `widget-data` keyed by the shape's id. Queries run with the permissions of the person on the connection: access level `user:{id}` searches with their own token (and `@me` is them, from `ConnectionAccess.login`); everyone else is `public`, whose searches get `is:public` added, run with any signed-in reader's token for the rate limit, and drop any result not known to be public (`@me` is an error). Results are cached per query and access level, so two tabs (or two widgets with the same search) cost one search. They refresh when a delivery reaches the board from a repository a query names, or its results came from, or for queries that search everywhere (`Board.repoActivity`, debounced, at most every 10 s), on the definition's `refresh` schedule (inboxes every minute), and on request (throttled). A per-access budget keeps searches well inside the forge's search limits, rate limits are waited out (`retryAt`), and a refresh that fails keeps the last good result, which the client shows as stale. Inbox results confirm the cards an inbox brought (`confirmMatches`). `related` and `release` queries run through the adapters too, keeping only public items for viewers without a token. Boards watch the repositories their queries read with `Repo.watch`, so `Repo`'s activity fan-out reaches them
- `src/server/webhooks.ts` — `POST /webhooks/:forge` routing
- `src/server/log.ts` — structured logger: one JSON line per event (see Observability)
- `src/server/clientErrors.ts` — `POST /api/client-errors`: browser error reports, logged as `client.error` events
- `src/server/snapshots.ts` — board snapshots for backlink comments: `POST /api/boards/:id/snapshots` (a PNG body, editors only, at most 1.5 MB and 4096px a side, 1000 per board) returns `{ url }`, and `GET /snapshots/:id.png` serves it publicly with a year's `immutable` caching (GitHub's image proxy fetches it). The id is the board object's id (which says nothing about the board) then 128 random bits, so serving an image never touches the board index, and only reads the snapshot table, never the board's document. Images live in the `Board` object's SQLite storage
- `src/shared/` — forge-neutral item keys (`{host}/{repo}{#|!}{n}`, see `refs.ts`), card types and the Yjs shape schema (`shapes.ts`, documented there), used by both server and client. Pure canvas logic lives here too, so it's unit-tested in Node and usable on the server: `geometry.ts`, `sections.ts` (containment), `connectors.ts` (ends and routing), `structure.ts` (structural edits), `repair.ts` (the repair pass for dangling references), `decisions.ts` (decision edits: votes in a nested Y.Map keyed by voter, status, linked items, the write-back), `adr.ts` (the pure ADR template, record numbering and the write-back operations), `provenance.ts` and `related.ts` (below), `widgetRegistry.ts` (the widget registry: each kind's `WidgetDefinition`, configs read through its Valibot schema field by field with defaults, the list widget, `addWidget`, `queryScope`) and `search.ts` (GitHub-style searches for widgets: parsing into terms, `searchScope`, `matchSearch` yes/no/unknown, and `planMatch`, the label, assignee, milestone and state changes that would make a card match a search, or why none can, for drop to match). For M3's automation: `query.ts` (a local reading of GitHub-style searches: `matchesQuery(card, query)` is true, false, or null when the card can't answer, e.g. `milestone:`), `mentions.ts` (references and closing keywords in a pull request's text), `placement.ts` (free space beside a shape or inside a section: never over a shape, across a section's edge or over its title), `inbox.ts` (inbox frames: `inbox` and a nested `dismissed` Y.Map on sections, the tray, sorting a match out with provenance `inbox`, and whether a card still matches) and `rules.ts` (the `rules` Y.Map, the `ruleLog` Y.Array, describing rules in words, and `runRules`, which the server and the playground both use)
- `src/shared/provenance.ts` — provenance (M3, #41): how each card arrived (`Provenance`: manual, list, inbox or rule) and what happens when it stops matching. **Every card is made through `addCardShape` (or the client's `addCard`, which takes the same optional provenance)**. Manual is the default and is never stored: a card without `provenance` was placed by a person, which includes pasting or typing a link, Expand related and copies of other cards (paste and duplicate drop `provenance` and `unmatched`, `CARD_UNCOPIED`). `whenUnmatched` decides: manual and list cards stay as they are (a list only ever copies), inbox and rule cards are marked. Whatever runs an inbox's or rule's query calls `updateMatches(doc, source, matches, { origin })`, which sets or clears the card's `unmatched` key (when it stopped matching) and never removes or moves a card; people then keep it (`keepCard`: it becomes manual, so it's never marked again) or remove it. `provenanceSourceName` and `describeProvenance` say where a card came from (a list widget's `config.title`, an inbox section's title, a rule's `name` in the document's `rules` map)
- `src/shared/related.ts` — Expand related's layout (#42), pure: `planExpand` puts the parent (or a pull request's closing issues) above, sub-issues below in rows of four, blocked-by to the left, blocking to the right and linked pull requests above those, each group sliding outward (and a little sideways) to the nearest spot clear of every other shape; items already on the board are connected where they are, and pairs already connected aren't connected again. `applyExpand` writes the plan (call inside `transactLocal`: one undo step). Connectors: hierarchy as elbows parent to child, `blocks` in red from blocker to blocked (as blocked-by staging reads them), pull requests dashed purple (`closes` when they do)
- `src/client/` — React + React Flow canvas (own `tsconfig.json` with DOM types); `index.html` at the repo root is its entry
- `src/client/undo.ts` — undo and redo with `Y.UndoManager`, tracking only this client's changes. **Every local document write must go through `transactLocal(doc, fn)`** (origin `LOCAL_ORIGIN`, `"local"`), or it can't be undone; changes from other people, the server and seeding are never undone. One transaction is one undo step
- `src/client/sections.tsx`, `src/client/connectors.tsx`, `src/client/canvasStructure.ts` — sections (React Flow nodes, containment through a stored `parent` key) and connectors (our own SVG layer inside the viewport); see `docs/react-flow-probe.md`
- `src/client/widgets/` — widgets on the board (#37, #38, #39): the widget node (`WidgetNode.tsx`: sized by the shape's `w` and `h`, picked up by its header, resized from the shared section grips when selected, its config panel beside it in a `NodeToolbar`), the board-free list view the gallery also uses (`ListView.tsx`: every state, rows that slide in, fold away and flash, the on-board pin, and the drop-to-match overlay), config panels (`ConfigPanel.tsx`: written for the list, generated from the schema for other kinds), the picker (the widget tool, W), dragging rows out as cards (`RowDrag.tsx`: a ghost at the board's zoom, made with `addCardShape` and provenance `{ via: "list", source }`), drop to match (`useDropToMatch.ts` catches card drops on lists, which glide back; `match.ts` plans and stages through `stageTriage` as one undo step; `DropConfirm.tsx`), and the data store (`store.ts`: `widget-data` by widget id, watched while mounted and for a few seconds after, through a swappable transport; the linked-highlight store between rows and cards; which items have cards on the board)
- `src/client/decisions/` — the decision node (`DecisionNode.tsx`, with the board-free `DecisionView.tsx` the gallery uses) and the write-back dialog, which stages an ADR pull request or a Discussion post as a pending change. Its repository endpoints go through the swappable `repoApi` (in `src/client/changes/api.ts`), which the playground fakes. A written-back decision stores its pull request as `ref`, so the board follows its live state like a card's
- `src/client/commands.ts` — keyboard shortcuts, clipboard, nudging and arranging; `shortcuts.ts` is the single list behind both the key handling and the `?` sheet. Shortcuts ignore keys typed into text fields. Clipboard and snapping (`clipboard.ts`, `snapping.ts`, `arrange.ts`) are generic over shape types: copy carries every property, and snapping uses measured bounds
- `src/client/boards/` — the home page (`/`), board routes (`/b/{id}/{slug}`, and `/?board=name` redirects), the renameable title, the share dialog, tiles and SVG thumbnails
- `src/client/changes/` — pending changes and pushing (M2): the push API client other code reuses (`api.ts`: `pushApi(boardId)`, a shared `RepoMetaCache`), the store over the document's `changes` map with stable per-shape snapshots (`store.ts`), how changes read, group, depend on each other and who they notify (`describe.ts`, pure), staging edits that keep dependencies whole and the push in progress (`session.ts`), and the UI: the top bar's Changes button, the panel, marks on shapes (`withStagedMarks` wraps every node type) and the push sheet with review, progress and history. Statuses arrive through the document, never by polling
- `src/client/auth/` — sign-in UI: the `/api/me` store (`me.ts`), the account menu, the access gate with the sign-in and "invite-only" pages, and the `/setup` page
- `src/client/actions/` — the selection actions (M2, #32 and #33): a bar under the selection (`ActionBar.tsx`) that stages stickies as issues, a section or cluster as a parent issue with sub-issues, and triage (labels, milestone, assignees, close/reopen) and backlinks on cards; blocked-by from a connector's toolbar (`BlockedBy.tsx`). Every action only stages pending changes (staging logic in `src/shared/actions.ts`, unit-tested), one undo step each, and offers only the writes the forge supports (`RepoMeta.writes`). Pickers (`pickers.tsx`) are keyboard-first; shortcuts are ⌥I, ⌥⇧I, ⌥L, ⌥M, ⌥P, ⌥C, ⌥B and ⌥K. Expand related (⌥E, `ExpandRelated.tsx`, M3) is the one action that doesn't stage anything: on a single card it fetches what's related through `WriteServices.related` (the board's related route), lets you switch groups off (a little compass shows where each goes), and lays them out, flying out from the card in turn (`src/client/entering.ts` choreographs entrances for shapes added together) while their connectors draw in; the view pans to show them if they're off screen. Backlink snapshots are drawn in the browser from the canvas DOM with modern-screenshot (`snapshot.ts`), one per audience: cards from other private repositories are replaced by a placeholder before the image is made (`src/shared/backlinks.ts`). `services.ts` is what they need from outside the document (repository metadata, snapshot uploads); the playground passes in fakes
- `src/client/inbox/` — inbox frames (#40): the tray on an inbox section's right edge (`InboxTray.tsx`, drawn in a `ViewportPortal` above every shape, growing against the zoom like section titles), where new matches wait marked new to be dragged out (a ghost card follows the pointer; it lands as a card with provenance `inbox`), clicked into the section, or dismissed (with Undo); the query editor with a live count (`InboxEditor.tsx`); and the store of results from `widget-data` (`store.ts`, reference-counted watching, wired to the live connection or the playground's simulation). "Make inbox" is on a section selected on its own
- `src/client/rules/` — the rules panel (#44), from the top bar's Rules button: rules in words with a switch to pause each and what it has done, a composer for the two kinds (linked pull requests beside their issue; matching items into a section, with the query checked as you type), recent activity ("Placed #431 beside #412, 2 min ago"; click to go to the card), and a toast when a rule places a card while you watch

Use these to iterate on interaction details

## Commands

- `pnpm dev` — start the dev server (`vp dev`). `cf dev` and `cf build` expect a `vite` binary, which Vite+ doesn't provide, so use `vp`
- `pnpm test` — unit and integration tests (`vp test`)
- `pnpm e2e` — Playwright smoke tests (`e2e/`). Starts its own dev server on port 5205 (or `E2E_PORT`), or reuses one already running there. Install the browser once with `pnpm exec playwright install chromium`
- `pnpm e2e:visual` / `pnpm e2e:update` — also run (or rewrite the baselines for) the opt-in pixel comparison of the gallery
- `pnpm check` — format check, lint, and type check in one pass (`vp check`)
- `pnpm fix` — apply formatting and safe lint fixes
- `pnpm build` — production build
- `pnpm run deploy` — `vp build` then `cf deploy --prebuilt` (requires `cf auth login` or `CLOUDFLARE_API_TOKEN`). Note the `run`: `pnpm deploy` is pnpm's own workspace command, not this script. Production deploys happen via Workers Builds, which runs this on every push to `main`, not from CI or local machines
- `pnpm run deploy:preview` — builds Preview Build Output (`CLOUDFLARE_PREVIEW_BUILD=true vp build`) then `cf previews deploy --prebuilt`. Workers Builds runs this for every branch other than `main`, so each branch gets a Worker Preview with its own URL and its own isolated Durable Objects. `CLOUDFLARE_PREVIEW_BUILD` is what `cf build` sets for preview builds; we set it ourselves because `cf build` expects a `vite` binary

## Configuration Architecture

- **`cloudflare.config.ts` is the source of truth for the Worker**: name, entrypoint, compatibility, bindings, observability. It uses `defineConfig({ worker: { ... } })` from `cf/config`, which both the `cf` CLI and the Vite plugin read.
- The entrypoint uses the `with { type: "cf-worker" }` import attribute. This is what makes `Env` and `exports` inference work — keep that form when changing the entrypoint.
- **Previews**: `cloudflare.config.ts` uses the function form of `defineConfig`, which receives `isPreview`. Previews don't inherit production settings, so it returns the complete config for both. Previews get no secrets (webhooks only go to production, and card fetches work unauthenticated), so the code must treat `GITHUB_WEBHOOK_SECRET`, `GITHUB_TOKEN` and `TACK_SECRET` as optional.
- **Bindings**: declare them in `cloudflare.config.ts` (e.g. `env: { MY_KV: bindings.kv() }` with `bindings` from the same import). The `Env` type is inferred from them — run `pnpm types` after config changes. Durable Object bindings to this same Worker are untyped; `src/server/namespaces.ts` restores the class types. Integration tests declare the same bindings for Miniflare in `test/harness.ts`, so keep the two in step.
- **`compatibility.ts`** exists so the test runtime (`test/harness.ts`) always matches the deployed runtime. Extra exports are not allowed in `cloudflare.config.ts` (its exports are schema-validated), which is why this is a separate file.
- **Version pins that must move together**: the `vite@*` and `vitest@*` overrides in `pnpm-workspace.yaml` pin Vite to `@voidzero-dev/vite-plus-core` at the installed `vite-plus` version, and Vitest to the version `vp toolchain vitest` reports. Update them whenever `vite-plus` changes. There are no direct `vite` or `vitest` dependencies: import test APIs from `vite-plus/test`.

## Auth and access

- **Secrets**: `TACK_SECRET` signs session cookies and encrypts stored credentials (keys derived with HKDF). Without it (Previews), sign-in and setup are off, `getViewer` returns null, and boards work anonymously. Code must keep working that way.
- **GitHub App**: created from a manifest at `/setup`; `/setup/callback` stores its credentials in `Instance`, and whoever completed setup becomes the first admin. Webhooks verify against the stored webhook secret, then `GITHUB_WEBHOOK_SECRET`. Installation tokens are minted with an app JWT, cached, and refreshed five minutes before expiry; repos map to installations from `installation`/`installation_repositories` events, or a lookup on a miss.
- **Sign-in**: the GitHub App's OAuth flow (state and PKCE) via `/auth/signin` → `/auth/callback`. Sessions are a random id in a signed, HTTP-only, SameSite=Lax cookie (Secure over HTTPS); only its hash is stored. User tokens are stored encrypted and refreshed (with rotation) by `viewerToken`.
- **Access**: once the app is set up, only admins, allowed users and members of allowed orgs (checked at sign-in) may use the instance; `canUseInstance(env, viewer)` says whether a viewer may. Before setup everything is open.
- **Boards**: each board has an owner, members (owner, editor, viewer; invited by GitHub login, resolved to an id when they first show up) and a visibility: private (members only), instance (anyone allowed on the instance, at the board's `instanceRole`) or public (also anyone at all, read-only, signed out). Membership needs instance access too; only public boards reach past the allowlist. Archived boards are read-only. `roleFor` in `src/server/boards/access.ts` decides. Live connections are checked per board in the Worker (`authorizeBoardConnection`), which passes the role to the `Board` object in a header it always overwrites; viewers get read-only connections (`isReadOnly`), and role changes reach open connections straight away (or close them with code 4403). Board membership never grants access to repo data: per-viewer card filtering (#10) goes in `Board.visibleCards`. Boards from before the index (`?board=name`) are adopted with their old name as id, so their documents carry over.
- **Dev sign-in**: with `TACK_DEV_AUTH=1` in `.dev.vars` (only declared for `vp dev`; never set it in production), `/auth/dev?login=octocat` signs in a fake user on loopback hosts. Options: `name`, `admin=1`, `allow=1` (add to the allowlist), `orgs=a,b` (pretend membership of allowlisted orgs), `return_to`. Dev users have negative ids.

## Testing

- Unit tests run in Node. Integration tests use `startWorker()` from `test/harness.ts`: `mf.dispatchFetch()` for HTTP, and `repoStub()`/`instanceStub()` (or `mf.getDurableObjectNamespace()`) for Durable Object RPC.
- Signed-in tests: `startWorker({ devAuth: true })`, then `const cookie = await signIn(mf, "octocat", { admin?, allowed?, orgs? })` and send it as the `cookie` header. Users are allowlisted unless `allowed: false`. To turn access control on, complete setup against the fake GitHub: `await (await instanceStub(mf)).completeSetup(github.manifestCode)` (see `test/boards.test.ts`).
- Board permissions are tested over real WebSockets with `connectBoard` from `test/board-client.ts`, a minimal Yjs sync client; `roundTrip()` waits until the server has applied everything sent before it. Boards must be in the index to connect: create them through `/api/boards` (or adopt one through `/api/boards/legacy`).
- Mock GitHub with `startWorker({ outboundService: github.fetch })`, where `github` is a `FakeGitHub` from `test/fake-github.ts`. It covers the app (manifest conversion, OAuth, users, org membership, installation tokens, the webhook delivery log; it verifies app JWTs against a test RSA key), repository data (repositories with renames, issues and PRs with CI and reviews, over REST and GraphQL) and writes (issues, labels, milestones, assignees, state, sub-issues, dependencies, comments, the git data API, pull requests and discussions, for each repository's `writers` where the app is installed; `failWrites` fails the next writes, `dropWrites` accepts them without doing them), and records `requests` so tests can count fetches. `userTokenFor` and `installationTokenFor` mint tokens for calling it directly, as `test/github-write.test.ts` does in Node.
- Pushing is tested end to end in `test/push.test.ts`: stage with `stageChange` on a `connectBoard` client's document, push through the route, and watch statuses arrive in the document. `boardStub(mf, id).pushTiming({ spacingMs, confirmMs, backoffMs })` shortens the engine's pauses. `failWrites({ status, match, after: true })` makes GitHub do a write but lose the answer. `github.event(repoId, n, action)` is an item's webhook payload as it is now, and `github.mergePull(repoId, n)` merges a pull request (its files land on `main`) and returns the `pull_request` payload; deliver them signed with the app's webhook secret. `signInWithGitHub` (harness) signs in through the fake OAuth flow, for a real user token. `test/m2-exit.test.ts` is the whole M2 exit session (#36) through the real GitHub adapter; keep it passing when changing actions, pushing or write-backs.
- Rules and inboxes are tested end to end in `test/automation.test.ts`: webhook deliveries to a board with rules in its document, and inbox sections searched on the synthetic `fake.tack` forge (whose `search` matches items 1–30 of the repositories a search names, with `matchSearch`). `BoardClient.send` sends custom messages (`widget-watch`, `inbox-preview`); `boardStub(mf, id).inboxTiming({ cacheMs, refreshMs, activityMs })` shortens the runner's waits.
- Widget queries are tested in `test/widget-queries.test.ts`, as people signed in through the fake GitHub (so each has a real token): what each viewer receives (raw messages, so a private repository's rows never reach someone who can't read it), caching per query and access level, refreshing on config changes and webhooks, and rate limits. `boardStub(mf, id).widgetTiming({ freshMs, debounceMs, minIntervalMs, throttleMs, inboxRefreshMs })` shortens the runner's waits, `runWidgets()` runs what's due and `widgetCache()` lists cached results without their data. The fake GitHub answers GraphQL and REST issue search (evaluated with `matchSearch`, gated by who can see each repository), and `failSearches(...)` makes the next searches fail.
- `test/github-data.test.ts` opens real boards over WebSockets, and restarts the Worker with `startWorker({ persist })` to test waking from sleep.
- End-to-end smoke tests are Playwright, in `e2e/`, kept out of `vp test` so it stays fast. They drive `/play` scenarios (render counts, simulated forge events, people joining, the sticky tool, dragging) and fail on any uncaught page error. When you add a `/play` scenario or gallery state, add it to `e2e/play.spec.ts` or `e2e/gallery.spec.ts`. `e2e/boards.spec.ts` and `e2e/m2-exit.spec.ts` run against real boards instead, signed in with `/auth/dev`: the latter is the M2 exit session through the UI on the fake forge, from staging to the push sheet and history (lay a board out by dispatching a `paste` of copied shapes, and read its document through the dev-only `window.tackBoard`).
- **Visual regression is opt-in for now.** The design is changing too fast for pixel baselines to be worth maintaining, so `e2e/gallery.spec.ts`'s screenshot test only runs with `VISUAL=1` (`pnpm e2e:visual`), and no baselines are committed. The gallery's structural checks (every card state, caption, `data-state` and label) always run and are what catch broken states. Turn pixel comparison back on once the UI settles, scoped to stable components rather than the whole gallery; the Test workflow's manual "update snapshots" run produces Linux baselines as an `e2e-linux-baselines` artifact.
- In CI, the `e2e` job runs separately from `test`, and uploads traces and failure screenshots as the `e2e-results` artifact. Open a trace with `pnpm exec playwright show-trace <trace.zip>`.

## Observability

- **Server logs** use `log` from `src/server/log.ts`: `log.info("webhook.verified", { repo, delivery })` writes one JSON line with `level`, `event` and the context. Use dotted event names and put identifiers in context fields rather than in the event name, so they can be filtered on. Errors passed in context are serialised with their stack.
- **Events**: `webhook.received`, `webhook.verified`, `webhook.ignored`, `webhook.rejected` (bad signature) and `webhook.failed`; `repo.ingest` (duplicate or processed, with update counts), `repo.fanout` (boards notified, failures) and `repo.fanout.failed`, `repo.fetch` (warns when the forge errored), `repo.refetch` (debounced CI and review refetches), `repo.reconcile` and `repo.reconcile.failed`, `repo.renamed`, `repo.visibility`, `repo.poll` (unchanged, changed or error) and `repo.poll.failed`, `repo.installation` and `repo.installation.watch.failed`; `board.load` and `board.save` (snapshot bytes and chunks), `board.save.failed`, `board.subscriptions.failed`, `board.connection.error` and `board.exception`, `board.route.resolved` and `board.route.unresolved` (repository name to id), `board.readable` (a viewer's read access to a private repository changed) and `board.readable.failed`, `board.send.failed`, `board.watch.failed`, `board.installation` and `board.installation.watch.failed`; `board.created`, `board.updated` (with the fields changed), `board.legacy.claimed`, `board.member.invited`, `board.member.updated`, `board.member.removed`, `board.member.resolved` (invites resolving to a GitHub id), `board.index.failed` (a save couldn't update the index), `board.access.failed` and `board.rename.failed` (telling a board's connections); `setup.completed` and `setup.failed`; `auth.signin` (with whether the person is allowed), `auth.signin.dev`, `auth.signin.failed` (with a reason), `auth.signout`, `auth.refresh.failed`, `auth.orgcheck.failed` and `auth.rejected` (cross-site); `access.denied` (including refused board connections, with the board and reason) and `access.updated`; `github.installation` (installation webhooks), `github.installation.failed`, `github.installation.notified` (Repos and boards told) and `github.token.failed`, `github.graphql.unavailable` (falling back to REST), `github.redelivery` and `github.redelivery.failed`; `push.started` (who, as whom, how many changes, which repositories), `push.rejected` (with the reason), `push.change.sent` (waiting for its card to show it), `push.change.applied` (with `via`: the forge's response, a card, or reconciliation), `push.change.retry` (rate limits and outages, with when), `push.change.failed` (with the error), `push.effect`, `push.completed` (counts by status), `push.healed` (document statuses brought back in line with storage), `push.access.failed`, `push.run.failed`, `repos.meta.failed` and `repos.files.failed`; `repo.activity` (a delivery's items sent to the boards with the repository, for rules and inboxes) and `repo.activity.failed`; `rule.placed` (rule, item, and the item or section it went beside or into), `rule.skipped` (with a reason: `no_section` or `no_room`) and `rule.failed`; `board.matches` (cards marked or unmarked as no longer matching, from a delivery); `widget.query` (a widget's or inbox's query ran: kind, `public` or `user` access, status, results, ms), `widget.query.failed`, `widget.send.failed`, `widget.refresh` (queries due again after a delivery) and `widget.watch.failed`; `snapshot.stored` (board, bytes, size), `snapshot.rejected` (with a reason: `cross_site`, `access`, `not_editor`, `type`, `not_png`, `size`, `dimensions` or `quota`) and `snapshot.missing`; `related.fetched` (board, key, `as` viewer or app, how many items, how many hidden from this viewer) and `related.failed` (with the reason); and `client.error`.
- **Client errors**: the app is wrapped in an error boundary with an on-brand fallback. Render errors, `window.onerror` and unhandled rejections are posted to `POST /api/client-errors` (at most 10 distinct errors per page load), which accepts reports up to 16 KB from the app's own origin, rate limits per client IP (in memory, per isolate; the IP is never logged), and logs a `client.error` event with the message, stack, component stack, path (no query string) and user agent. No third-party service is involved.
- **Finding logs in production**: Workers Logs is enabled (`observability` in `cloudflare.config.ts`). In the Cloudflare dashboard, open Workers & Pages → `tack` → Observability, and filter on fields such as `event = client.error` or `level = error`. JSON fields are indexed automatically. From a terminal, `cf o11y telemetry query` runs the same queries against the Workers Observability API (see `cf schema o11y telemetry query` for the request body), and `cf o11y telemetry live-tail` prepares a live tail.
- **Finding logs locally**: the dev server prints log lines to the terminal, and also keeps them queryable through the Cloudflare local explorer: `curl -X POST http://localhost:5173/cdn-cgi/local/explorer/api/local/observability/query -H 'content-type: application/json' -d '{"sql":"SELECT ts_ms, level, message FROM logs ORDER BY ts_ms DESC LIMIT 20"}'` (use your dev server's port). The e2e tests use this to check that a crash on `/play/crash` lands as a `client.error` event.

## Development Workflow

- Uses **pnpm**, wrapped by **Vite+** (`vp`). Format and lint are oxfmt/oxlint via `vp check` — there is no prettier or eslint. Type checking runs inside `vp check` (tsgolint with `typeAware`/`typeCheck` enabled).
- Formatting uses tabs (configured in `vite.config.ts` under `fmt`).
- CI (test.yml) runs `vp check`, `vp test`, and `vp build` via the `voidzero-dev/setup-vp` action in the `test` job, and the Playwright smoke tests in a separate `e2e` job, with the browser cached by Playwright version.
