This file provides guidance to agentic coding tools when working with code in this repository.

## Design principle: delight

The UI must be delightful, with FigJam as the bar: considered typography, micro-interactions, and lots of small details (how a card lifts when picked up, how a live update lands, how a push confirms). Treat polish as a feature, not a follow-up. Respect `prefers-reduced-motion`, and keep interactions at 60fps.

## Repository Structure

Tack: a GitHub-native collaborative whiteboard for open source planning, built as a Cloudflare Worker with Vite+ and the Cloudflare Vite plugin.

- `src/index.ts` — the Worker entrypoint: webhook route, partyserver routing, DO exports
- `src/server/board.ts` — `Board` Durable Object (one per board): Yjs document via y-partyserver, live card relay via custom messages, filtered per connection so private cards only reach viewers who can read them (`visibility.ts`), and watching its repositories while anyone's connected
- `src/server/repo.ts` — `Repo` Durable Object (one per repository, keyed by its id): card cache, board subscriptions, webhook log and fan-out, debounced CI refetches, reconcile on wake, repository status (`live`, `writable`, `visibility`), and ETag polling of repositories without the app while a board has them open (see `docs/github-data.md`)
- `src/server/routing.ts` — maps repository names to `Repo` objects by stable repository id, so renames don't split caches (see `docs/github-data.md`)
- `src/server/instance.ts` — `Instance` Durable Object (a singleton, `instance(env)`): the GitHub App's credentials, installations and their tokens, users, sessions and the access allowlist. Every credential is encrypted at rest with `TACK_SECRET`
- `src/server/directory.ts` — `Directory` Durable Object (a singleton, `directory(env)`): the board index. Boards (id, slug, title, owner, visibility, archived), members by GitHub login, visits ("Recent") and each board's thumbnail sketch. Separate from `Instance` so board traffic (a thumbnail update on every board save) stays off the session-lookup path
- `src/server/boards/` — board access (`access.ts`: `roleFor`, the one function deciding owner/editor/viewer from visibility and membership), the `/api/boards` routes and the per-board check on live connections (`routes.ts`, with what they share with the template routes in `http.ts`), and templates and carrying action items over (`templates.ts`: `GET`/`POST /api/templates`, `DELETE /api/templates/:id`, `POST /api/boards/:id/carry`, and `createBoard`, which `POST /api/boards` uses to lay a new board out from a template (`template`, `repos`) and carry the open action items of another (`carryFrom`)). Thumbnail sketches are drawn in shared code (`src/shared/thumbnail.ts`), so templates are sketched the same way
- `src/server/identity.ts` — the identity contract other code uses: `getViewer(request, env)` (HTTP and WebSocket upgrades), `viewerToken(env, viewer)` and `canUseInstance(env, viewer)`
- `src/server/auth/` — sign-in and sessions: `/auth/*` and `/api/me` routes (`routes.ts`), the GitHub OAuth flow with PKCE and refresh (`oauth.ts`), signed session cookies (`session.ts`), instance access checks (`access.ts`), and HKDF/AES-GCM/HMAC helpers (`crypto.ts`)
- `src/server/migrations.ts` — Durable Object SQLite migrations (#55): `migrateSql(sql, scope, migrations)` runs a part's migrations once each, in order, recording where each scope got to in `schema_versions`; `addColumn` for idempotent ones. See "Format versions and migrations" below
- `src/server/github/` — the GitHub App: manifest and RS256 app JWTs (`app.ts`), `/setup/*` and `/api/setup*` routes (`setup.ts`), whether webhooks reach the instance, read from the app's webhook settings and delivery log (`webhookHealth.ts`, `Instance.webhookHealth`, for `/setup`'s checks), webhook verification and installation events (`webhooks.ts`), and the token contract (`tokens.ts`: `repoToken`, `isInstalled`, `appJwt`) that everything reading GitHub goes through, plus the cron that redelivers failed webhooks (`redeliver.ts`)
- `src/server/forges/` — forge adapters (GitHub; GitLab, Forgejo and Tangled, #65, see below; plus a synthetic `fake.tack` forge for tests and stress boards): fetching items, verifying and normalising webhooks, capabilities, and writing (`apply`, `canWrite`, `repoMeta`, `listDirectory`, and `writeBranch` for backups, #59; GitHub's are in `github-write.ts`), answering comment commands as the app (`react`, `unreact`, `reply`, #58; GitHub's are in `github-commands.ts`), and reading for widgets (`search`, `related`, `release`; GitHub's search is in `github-search.ts`: GraphQL's `search` with a token, so results are full cards that say whether their repository is private, and anonymous REST issue search without one; once GitHub rate limits a token, that isolate stops searching with it until GitHub says). Everything outside this folder is forge-neutral. `apply` never throws for forge errors: they come back as results, rate limits retryable with `retryAt`, and `ApplyOptions.retryOf` makes creates look for what an unanswered earlier attempt made before making it again. Refusals the board can offer a way out of carry a `problem` (`ChangeProblem` in `src/shared/changes.ts`: a sub-issue that already has a parent, loops, limits, an issue linked to itself, repositories GitHub won't link), mapped from GitHub's 422s in `github-write.ts`; sub-issues take `replaceParent` (GitHub's `replace_parent`) to move a child from the parent it has. The fake forge's writes succeed without a network (anything with `[fail]` in it is refused), sub-issues and blocked-by included (its synthetic issues have a parent, `fakeParent`, so a second one is refused unless moved), and its repositories count as writable without any app, so the whole push flow can be tried locally without GitHub. Items it creates are numbered from 100000 (even for issues, odd for pull requests), and their cards are open items of that kind
- `src/server/push/` — pushing staged changes (M2): the routes (`routes.ts`: `POST /api/boards/:id/push`, `GET /api/boards/:id/pushes`, `GET /api/repos/meta`, `GET /api/repos/files`), planning a push (`plan.ts`: checking operations from the document, dependency order, summaries), and the engine each `Board` runs (`engine.ts`). The engine snapshots what was pushed in the board's SQLite storage, applies it one write at a time from the board's alarm (a second apart, in batches, waiting out rate limits in order), writes statuses into the document with `PUSH_ORIGIN` (never undoable), confirms `sent` changes when the card shows them (`reflects` in `src/shared/confirm.ts`; the board subscribes to those items), reconciles ones that don't confirm in time, runs change effects (`replace`: shapes become the created item's card, in place; `place`: a card for the created item above the shapes it came from, connected to them, as a section's parent issue gets, `placeCard` in `src/shared/place.ts`, which slides it clear of other shapes as Expand related does), and keeps the audit log. SQLite is the truth: a change being pushed or applied is never pushed again, whatever the document says
- Other forges (#65): `gitlab.ts`/`gitlab-write.ts`/`gitlab-api.ts`, `forgejo.ts`/`forgejo-write.ts`/`forgejo-api.ts` (Codeberg, and Gitea) and `tangled.ts` (read-only: an item's AT-URI read once from its page and kept as the card's `nodeId`, then Tangled's XRPC index), sharing `rest.ts` (calls through `forgeFetch` with a timeout, failures in plain words naming the forge, `segments`, `iso`). Which hosts an instance serves, with their tokens, webhook secrets and writes, is `config.ts`: `gitlab.com`, `codeberg.org` and `tangled.org` by default, read anonymously, and `TACK_FORGES` (an optional secret, JSON) adds self-hosted ones, credentials, `writes` and `writers` (GitHub logins), or turns a default `off`. Every entry point calls `configureForges(env)` (the Worker's handlers, and each Durable Object's constructor) so `parseKey`/`parseRef` know the hosts; the client gets them (no credentials) as `forges` in `/api/me`. Their reads and writes always use the instance's own token for the host (never a viewer's GitHub token), so `canRead` is true only for public repositories (nobody sees anything else), `canWrite` takes the pusher's login (`mayWrite`), `writable` says whether the instance writes there at all, and `apply` ignores `WriteAuth`. They have no app to install: `liveFromDeliveries` makes a repository live for a week after a verified delivery (`Repo`'s `delivered` meta) and polled while watched otherwise (Tangled sends none, so it's always polled). Webhooks find their host from the payload's repository URL and verify against that host's secret: Forgejo's bare-hex HMAC (`verifyHexSignature`, `X-Forgejo-Signature` or `X-Gitea-Signature`), GitLab's token compared in constant time (`sameSecret`). Keys: `#` for GitLab issues and `!` for merge requests (nested groups allowed; the path is one encoded API segment), `#` for everything on Forgejo, `#`/`!` for Tangled's issues and pulls; Forgejo and Tangled repository paths must be exactly `owner/name` (`fitsForge` in `refs.ts`). Capabilities say what each can write, and the UI only offers those. The client calls a repository on these forges "checked" (`repoStatus.ts`) rather than offering the GitHub App, and the push sheet hides "push as" for them
- `src/server/related.ts` — `GET /api/boards/:id/related?key=…` (M3, #42): what's related to an item (parent, sub-issues, blocked-by, blocking, linked pull requests; `related` on the forge adapter, in `github-related.ts` for GitHub along with `release`), for anyone who can open the board, as they may see it: asked with their own token, and anything from a repository that isn't public that they can't read is left out entirely, keys and all
- `src/server/itemSearch.ts` — `GET /api/boards/:id/search?host=…&q=…`: the card tool's search (C), for anyone who can open the board, run with their own token (results are what they can see); without one, only public items (`is:public`, and anything not known to be public dropped), as a widget's public searches are. At most `ITEM_SEARCH_LIMIT` results
- `src/server/rules.ts` — the rules engine (#44): each `Board` runs its rules (`src/shared/rules.ts`) on every webhook delivery it hears about (`Board.repoActivity`, called by `Repo` for every board subscribed to any of its items, or watching it for an inbox, with the delivery's items under each board's keys and what a pull request's text mentions or closes, `Delivery.mentions`). Rules run with the app's access (the delivery's data) and only place items from repositories already on the board, or chosen for it when it was made from a template (`scopeRepos`: the document's `scope.repos`, written by `Board.seed`); they write with `RULE_ORIGIN` (never undoable), and which items each rule has placed is kept in the board's SQLite (`rule_placed`), so a rule never places an item twice, even after someone removes it. The same pass keeps "no longer matches" marks (`unmatched`, see `provenance.ts`) current for cards an inbox or a matching rule brought, from the delivery's data (`refreshMatches`); an inbox's results only ever clear marks (`confirmMatches`), since one viewer's results leaving a card out may just mean they can't read it. Rules can be paused for a live session (`pauseRules`/`resumeRules`, the document's `rulesPause` map: `paused` written by whoever paused, under the non-undoable `RULES_PAUSE_ORIGIN`, and `held` by the server): while paused, deliveries are kept in SQLite (`rule_held`, the last `HELD_KEEP`) and counted in `held`, and run in order the moment the pause is lifted (the engine observes `rulesPause`), or before the next delivery
- `src/server/commands.ts` — comment commands (#58), see "Comment commands" below: each `Repo` keeps the commands left in comments on its items (`comment_commands`, by comment id, so each comment runs once) and runs them from its alarm (`CommentCommands`), retrying when the forge falls over; the checks (who asked, which board, private repositories), placing through `Board.addFromCommand`, and answering with reactions and a reply as the app. GitHub's half (reading `issue_comment` deliveries, reacting and replying) is `src/server/forges/github-commands.ts`, the pure half (parsing, matching boards and sections by name, placing, replies) `src/shared/commands.ts`
- `src/server/widgets/runner.ts` — the widget runner (#37), one per `Board`: it runs the queries of every widget (`widgetQueries` from the registry) and inbox section (one query named `inbox`, #40) that a connection watches (`widget-watch`/`widget-unwatch`/`widget-refresh` with shape ids; `inbox-preview` for an inbox editor's live count, answered under `previewId(section)`), and sends `widget-data` keyed by the shape's id. Queries run with the permissions of the person on the connection: access level `user:{id}` searches with their own token (and `@me` is them, from `ConnectionAccess.login`); everyone else is `public`, whose searches get `is:public` added, run with any signed-in reader's token for the rate limit, and drop any result not known to be public (`@me` is an error). Results are cached per query and access level, so two tabs (or two widgets with the same search) cost one search. They refresh when a delivery reaches the board from a repository a query names, or its results came from, or for queries that search everywhere (`Board.repoActivity`, debounced, at most every 10 s), on the definition's `refresh` schedule (inboxes every minute), and on request (throttled). A per-access budget keeps searches well inside the forge's search limits, rate limits are waited out (`retryAt`), and a refresh that fails keeps the last good result, which the client shows as stale. Inbox results confirm the cards an inbox brought (`confirmMatches`). `related` and `release` queries run through the adapters too, keeping only public items (and items from public repositories) for viewers without a token. Definitions work out their queries from their config and a `QueryContext` (the time, for relative ranges; the cards in a section, for kinds that say `readsBoard`, read again when cards move between sections), and may ask for `followUps` from their first results (a dependency map's `related` per search result, at most `MAX_FOLLOW_UPS`), which run with the same caching and arrive in the same message. Searches and other reads have separate per-minute budgets. Boards watch the repositories their queries read with `Repo.watch`, so `Repo`'s activity fan-out reaches them
- `src/server/comments.ts` — comments on the server (#51): `CommentsService` keeps threads and messages in the board object's SQLite storage (not the document: viewers can comment but can't write it, the server stamps who wrote each message, and read state is private; see `src/shared/comments.ts`), checks every `comment-*` request from a connection (rate limited per connection), and the board sends the whole thread to everyone connected. Viewers who are signed in can comment, reply, and resolve or move their own threads; editors and owners can resolve and move anyone's; people edit and delete only their own messages, and owners can delete anyone's (deleted messages can be restored by their author for ten minutes, for Undo). Signed-out visitors to public boards read comments but can't write them, and archived boards are read-only for everyone. Mentions are checked against the board's people (`Directory.mentionable`: members, and people who've opened it lately) and notify them, as replies notify the others in a thread, through `Directory.notify`. Pins on a shape keep their resting point in step with it (`shapeMoved`), so they stay where it was if it's deleted. Read state is per person (`comment_reads`), sent only to their own connections
- `src/server/since.ts` — since you were here (#46) on the server: `ChangeLog` watches the document and keeps one row per shape and kind of change (added, moved, changed, removed: the latest, with who, from the transaction's origin: a connection, a rule or a push; repairs aren't anyone's), buffered and flushed with saves; `CardHistory` keeps a dozen snapshots per card (state, comments, CI, review) whenever one changes; `Visits` remembers each signed-in person's first visit, when they were last here (on leaving, and every minute while here) and the visit their digest is since, a new visit starting after 15 minutes away (`VISIT_GAP_MS`), so reloads keep the digest. The board answers `since-request` with a `Digest` of other people's edits, card activity (only for repositories the viewer can read) and pushes since then, and `since-seen` ("Mark all as seen") starts again from now. Signed-out people send the time their browser remembers
- `src/server/boards/people.ts` — `GET /api/people?q=` (people who've signed in here, by login or name, for invite suggestions) and `GET /api/people/:login` (who a login is: `known` here, on `github`, `unknown`, an `organization`, or `unchecked` when GitHub can't be asked), asked with the viewer's own token and cached per isolate. Invites (`POST /api/boards/:id/members`) refuse logins GitHub says don't exist or are organisations (`unknown_login`, with the logins), so a typo never sits in a board's list as "invited"; without a token (dev sign-in, Previews) they go through unchecked
- `src/server/notifications.ts` — `GET /api/notifications` and `POST /api/notifications/read`: the top bar's inbox of mentions and replies, kept by the `Directory` per person (their latest 200), from boards they can still open
- `src/server/facilitation.ts` — facilitation on the board's server (M4, #50 and #49): `Facilitation` answers `clock` pings with the server's time, writes the shared timer into the document in the server's clock (`timer` requests, editors only), holds spotlight in memory tied to the spotlighter's connection (editors only; it ends when they leave, latecomers are told on connect, and the owner or whoever's running the session can take it over or end it), tells each connection who it is (`facilitation-you`) and who's here (`facilitation-present`), refuses timer and spotlight requests from people who mayn't (`not_facilitator`), broadcasts `timer-changed` (for "Kai stopped the timer"), runs `VoteGuard` over the document, and runs silent mode's `SilentHub` (`src/shared/silentHub.ts`) over the board's SQLite (`silent_sessions`, `silent_texts`). Each connection's requests are handled in order. Who someone is, for owning hidden text, is their GitHub user id, or for a guest the SHA-256 of a random secret their browser keeps (`silent-hello`; at least 16 characters, else just the connection)
- `src/server/ai.ts` — Workers AI (#73), the one place the server asks a model: `aiStatus(env)` (`TACK_AI` and whether the `AI` binding is there: on, off or unavailable, shown on `/setup`) and `askModel(env, request)`, one structured-output request to `AI_MODEL` (Gemma 4 26B A4B; GLM-4.7 Flash, `AI_FALLBACK_MODEL`, takes the same request). What's asked and how answers are read belong to each feature. See "Stacks and AI suggestions" below
- `src/server/stacks.ts` — stacks on the board's server (#73): `Stacks` runs the shared `StackNamer` with Workers AI (`stackAi`, via `askModel`, or local dev's stand-in), a cache of names in the board's SQLite (`stack_names`), and answers `stack-group` (Group these) for editors only
- `src/server/history.ts` — board history on the server (M4, #47): the `HistoryStore` over the board's SQLite (`history_steps`, `history_keyframes`, `history_blobs` with updates and keyframes chunked like the snapshot, `history_actors`, `history_meta`), who made each update (`attributeOrigin`: a client's connection is its GitHub id and login from the Worker's access check, with the name, colour and avatar its client shows; the server's own origins are `sys:push`, `sys:rule`, `sys:reveal`, `sys:timer`, `sys:repair` and `sys:server`), and the routes: `GET /api/boards/:id/history` (the `Timeline`) and `GET /api/boards/:id/history/segment?step=N` (a `Segment` as bytes), for anyone who can open the board. `Board` starts its `HistoryLog` right after loading (before anything else writes), flushes it before every snapshot save, and saves with every timeline read, so history is never ahead of what's saved. See "History" below
- `src/server/ai/` — AI on boards (#64), see "AI" below: the route (`routes.ts`: `POST /api/boards/:id/ai`), asking (`model.ts`: `ask`, over `askModel` in `src/server/ai.ts`, with a time limit and the conversation's later turns), each board's budget (`limits.ts`, `AiBudget`) and what a board lets the model read (`board.ts`, `BoardAi`, run by `Board.aiPrepare`)
- `src/server/webhooks.ts` — `POST /webhooks/:forge` routing
- `src/server/securityHeaders.ts` — security headers (#60): the app's CSP (`appCsp`, scripts only from the app and by hash), the `_headers` file the build writes for the static assets (`headersFile`, from `vite.config.ts`), and `withSecurityHeaders`, which `src/index.ts` puts on everything the Worker answers. See "Security" below
- `src/server/awareness.ts` — presence as the board relays it (#60): `sanitizeAwareness` checks every awareness update from a connection (who people are comes from their sign-in, a connection only speaks for its own few client ids, states are bounded), and `Board` relays what changed to everyone in batches every 40 ms
- `src/server/compaction.ts`, `src/shared/compaction.ts` — compacting very old boards' documents (#60), see "Compaction" below
- `src/server/log.ts` — structured logger: one JSON line per event (see Observability)
- `src/server/forges/rateLimit.ts` — one rate-limit backoff for every forge call (#60): `forgeFetch` is `fetch` for forge APIs, every GitHub call goes through it (REST, GraphQL, the app's own calls and the redelivery cron). It reads GitHub's primary limits (`x-ratelimit-remaining`/`-reset`), secondary ones (`retry-after`, or said in words, waited out for at least a minute and longer each time they recur within 15 minutes) and GraphQL's `RATE_LIMITED` (`noteBodyLimit`), keeps them in a per-isolate gate by token (hashed, never kept) and resource, and while one holds answers 429 with `retry-after` itself, without calling GitHub. Callers read any response with `rateLimitOf`, so the push engine, widget runner, comment commands and polling all wait for the same `retryAt`; `forge.rate_limited` is logged once per limit
- `src/server/exports.ts`, `src/server/backups.ts` — export, import and backups (#59), see "Export, import and backups" below: `POST /api/boards/import` (a new board from an export, read with `readBoardExport`, laid out by `Board.importContent`), and `GET`/`PUT`/`DELETE /api/boards/:id/backup` and `POST /api/boards/:id/backup/run` (backups to a branch: editors read, the owner changes). `Backups` runs on each `Board` (its SQLite `backup` table and the alarm it shares with the push engine, `Board.alarmAt`); `checkTarget` is the one check of where a backup may go
- `src/server/clientErrors.ts` — `POST /api/client-errors`: browser error reports, logged as `client.error` events
- `src/server/snapshots.ts` — board snapshots for backlink comments that ask for one: `POST /api/boards/:id/snapshots` (a PNG body, editors only, at most 1.5 MB and 4096px a side, 1000 per board) returns `{ url }`, and `GET /snapshots/:id.png` serves it publicly with a year's `immutable` caching (GitHub's image proxy fetches it). The id is the board object's id (which says nothing about the board) then 128 random bits, so serving an image never touches the board index, and only reads the snapshot table, never the board's document. Images live in the `Board` object's SQLite storage
- `src/server/embeds/` — public boards outside Tack (#56, #57), see "Public boards and embeds" below: the routes (`routes.ts`: `GET /embed/:id.svg|png` images of a public board or part of it, `GET /og/:id.png` link preview images, and `/b/:id/*` pages with link preview meta tags, rewritten with `HTMLRewriter` from the `ASSETS` binding), drawing a scene as Satori's element tree (`draw.ts`, pure, unit-tested in Node; colours in `palette.ts`, copied from the tokens in `styles.css`), and Satori and resvg as WebAssembly (`render.ts`, loaded on first use; the fonts are `.woff.bin` data modules in `fonts/`, with their OFL licences)
- `src/shared/embed.ts` — what a board image shows, pure: image options read from and written to addresses (`parseEmbedQuery`, `embedQuery`, `embedPath`, `ogPath`), the snippets Copy embed copies (`embedSnippet`), and `buildScene`, which lays out shapes and cards as someone signed out sees them (private repositories' cards as bare placeholders, silent stickies face down, widgets without results; the one place those rules live), plus `countBoard`/`describeBoard` for link previews and `clean` (text the image fonts can draw)
- `src/shared/` — forge-neutral item keys (`{host}/{repo}{#|!}{n}`, see `refs.ts`), card types and the Yjs shape schema (`shapes.ts`, documented there), used by both server and client. Pure canvas logic lives here too, so it's unit-tested in Node and usable on the server: `geometry.ts`, `sections.ts` (containment), `connectors.ts` (ends and routing), `structure.ts` (structural edits), `repair.ts` (the repair pass for dangling references), `decisions.ts` (decision edits: votes in a nested Y.Map keyed by voter, status, linked items, the write-back), `adr.ts` (the pure ADR template, record numbering and the write-back operations), `provenance.ts` and `related.ts` (below), `widgetRegistry.ts` (the widget registry: each kind's `WidgetDefinition`, configs read through its Valibot schema field by field with defaults, the list widget, `addWidget`, `queryScope`) the widget kinds' own pure logic: `timeline.ts` (ranges, the search with its date qualifier, ticks, stacking and clusters, density), `releaseDraft.ts` (sections by label, contributors, the next version, Markdown notes) and `dependencyMap.ts` (the blocked-by graph, cycles, layered layout, critical path, and planning it onto the board as cards and `blocks` connectors), and the review queue, milestone and stale finder (`review.ts`: a pull request's wait, size and review standing, oldest first; `milestone.ts`: progress, the burn-up from items' `createdAt` and `closedAt`, pace and forecast, due dates and what's at risk; `stale.ts`: the search with its `updated:<` cutoff, groups by how long items have been quiet, and the ping comment), with `widgetContext.ts` (`boardQueryContext`: what a widget's queries may read from the board), and `search.ts` (the one reading of GitHub-style searches, for widgets, the fake forges, rules and inboxes: parsing into terms, `searchScope`, `matchSearch` yes/no/unknown, its local reading for rules and inboxes, `matchesQuery(card, query)`, true, false, or null when the card can't answer, e.g. `milestone:` or `@me`, with words decided by the title, and `unsupportedForRules`; and `planMatch`, the label, assignee, milestone and state changes that would make a card match a search, or why none can, for drop to match). For M3's automation: `mentions.ts` (references and closing keywords in a pull request's text), `placement.ts` (free space beside a shape or inside a section: never over a shape, across a section's edge or over its title), `inbox.ts` (inbox frames: `inbox` and a nested `dismissed` Y.Map on sections, the tray, sorting a match out with provenance `inbox`, and whether a card still matches) and `rules.ts` (the `rules` Y.Map, the `ruleLog` Y.Array, describing rules in words, and `runRules`, which the server and the playground both use)
- `src/shared/ai.ts`, `src/shared/aiContext.ts`, `src/shared/aiPlace.ts` — AI's shared half (#64): the request and answer types, prompts and answer formats, `checkWidget` (a proposed widget checked strictly against its kind's schema; `WIDGET_GUIDES` describes every kind and field to the model, and `test/ai.test.ts` fails on one that's missing), the `widget-preview` message; what the model reads of a selection (`collectItems`: face-down stickies and cards the asker can't read are counted, never read); placing what's drafted (`placeSummary`, `placeDecision`); and the stand-in model for local dev and the playground (`fakeBoardAi.ts`)
- `src/shared/schema.ts` — board document versions and migrations (#55): the stamp (`meta.schema`, `boardSchema`), `BOARD_MIGRATIONS` (ordered, idempotent; `BOARD_SCHEMA` is the newest) and `migrateBoard`, which `Board` runs on every load. See "Format versions and migrations" below

## Configuration Architecture

- **`cloudflare.config.ts` is the source of truth for the Worker**: name, entrypoint, compatibility, bindings, observability. It uses `defineConfig({ worker: { ... } })` from `cf/config`, which both the `cf` CLI and the Vite plugin read.
- The entrypoint uses the `with { type: "cf-worker" }` import attribute. This is what makes `Env` and `exports` inference work — keep that form when changing the entrypoint.
- **Previews**: `cloudflare.config.ts` uses the function form of `defineConfig`, which receives `isPreview`. Previews don't inherit production settings, so it returns the complete config for both. Previews get no secrets (webhooks only go to production, and card fetches work unauthenticated), so the code must treat `GITHUB_WEBHOOK_SECRET`, `GITHUB_TOKEN` and `TACK_SECRET` as optional.
- **Secrets**: a secret declared with `bindings.secret()` is _required_ on deploy (a new Worker's first deploy fails without it; `--secrets-file` gives it), and deploys keep secrets that aren't declared. So production declares only `TACK_SECRET`; the optional `GITHUB_WEBHOOK_SECRET`, `GITHUB_TOKEN` and `TACK_FORGES` (and `TACK_DEV_AUTH`) are declared only in `mode === "development"`, so `.dev.vars` can set them, and are kept in production when set on the Worker. Don't declare a new optional secret for production: it would break every new instance's first deploy.
- **The Deploy to Cloudflare button** reads `wrangler.jsonc` (generated, see above), prompts for the secrets in `.dev.vars.example`, and runs `package.json`'s `deploy` script, which deploys with `cf`. It deploys the name in `cloudflare.config.ts`, so the Worker must keep its name there. The docs' self-hosting pages (`deploy.mdx`, `configuration.md`, `upgrades.md`) describe it and its limits.
- **Bindings**: declare them in `cloudflare.config.ts` (e.g. `env: { MY_KV: bindings.kv() }` with `bindings` from the same import). The `Env` type is inferred from them — run `pnpm types` after config changes. Durable Object bindings to this same Worker are untyped; `src/server/namespaces.ts` restores the class types. Integration tests declare the same bindings for Miniflare in `test/harness.ts`, so keep the two in step.
- **`compatibility.ts`** exists so the test runtime (`test/harness.ts`) always matches the deployed runtime. Extra exports are not allowed in `cloudflare.config.ts` (its exports are schema-validated), which is why this is a separate file.
- **Version pins that must move together**: the `vite@*` and `vitest@*` overrides in `pnpm-workspace.yaml` pin Vite to `@voidzero-dev/vite-plus-core` at the installed `vite-plus` version, and Vitest to the version `vp toolchain vitest` reports. Update them whenever `vite-plus` changes. There are no direct `vite` or `vitest` dependencies: import test APIs from `vite-plus/test`.

## Auth and access

- **Secrets**: `TACK_SECRET` signs session cookies and encrypts stored credentials (keys derived with HKDF). Without it (Previews), sign-in and setup are off, `getViewer` returns null, and boards work anonymously. Code must keep working that way.
- **GitHub App**: created from a manifest at `/setup`, which shows a checklist of getting the instance ready (secret, app, webhooks, repositories, people) and for admins also lists every installation, its repositories and whether Tack can push there (`GET /api/setup/installations`, `Instance.installations()`, straight from GitHub; it remembers the repositories it sees, as an installation event would; `notInstalled` lists repositories Tack looked the app up for and didn't find it, from `Instance.notInstalled()`), and whether webhooks arrive (`GET /api/setup/webhooks`, `Instance.webhookHealth(origin)`: the app's hook config and delivery log, assessed by `assessWebhooks` as `ok`, `waiting`, `failing` with a reason, `elsewhere`, `local` or `unknown`); `/setup/callback` stores its credentials in `Instance`, and whoever completed setup becomes the first admin. Webhooks verify against the stored webhook secret, then `GITHUB_WEBHOOK_SECRET`. Installation tokens are minted with an app JWT, cached, and refreshed five minutes before expiry; repos map to installations from `installation`/`installation_repositories` events, or a lookup on a miss.
- **Sign-in**: the GitHub App's OAuth flow (state and PKCE) via `/auth/signin` → `/auth/callback`. Sessions are a random id in a signed, HTTP-only, SameSite=Lax cookie (Secure over HTTPS); only its hash is stored. User tokens are stored encrypted and refreshed (with rotation) by `viewerToken`. Where sign-in and setup return people to (`return_to`, `state`) is only ever a path on this site (`safeReturnTo` in `src/shared/returnTo.ts`, used by the server's redirects and the `/signin` page alike).
- **Cross-site requests**: `src/index.ts` turns away every request that could change something (any method but GET, HEAD and OPTIONS) and every live connection whose `Origin` or `Sec-Fetch-Site` says it came from another site (`isCrossSite`, logged as `auth.rejected`), before any route sees it. Webhooks are the one exception: they're signed. Routes keep their own checks too.
- **Access**: once the app is set up, only admins, allowed users and members of allowed orgs (checked at sign-in) may use the instance; `canUseInstance(env, viewer)` says whether a viewer may. Before setup everything is open.
- **Boards**: each board has an owner, members (owner, editor, viewer; invited by GitHub login, resolved to an id when they first show up) and a visibility: private (members only), instance (anyone allowed on the instance, at the board's `instanceRole`) or public (also anyone at all, read-only, signed out). Membership needs instance access too; only public boards reach past the allowlist. Archived boards are read-only. `roleFor` in `src/server/boards/access.ts` decides. Live connections are checked per board in the Worker (`authorizeBoardConnection`), which passes the role to the `Board` object in a header it always overwrites; viewers get read-only connections (`isReadOnly`), and role changes reach open connections straight away (or close them with code 4403). Board membership never grants access to repo data: per-viewer card filtering (#10) goes in `Board.visibleCards`. The push audit log and the digest's pushes go through `Board.redactAudit` too: a change to a repository that isn't known to be public (`Board.knownPublic`) reads "A change to a private repository" for viewers who can't read it (the route uses `pushLogFor(userId)`; `pushLog()` over RPC is unfiltered, for tests). The access header also carries whether the board is archived and, for signed-in people, their login, name and avatar (URI-encoded, as names needn't be Latin-1), for attributing comments and edits. Comments are the one thing viewers can write: see `src/server/comments.ts`. Boards from before the index (`?board=name`) are adopted with their old name as id, so their documents carry over.
- **Dev sign-in**: with `TACK_DEV_AUTH=1` in `.dev.vars` (only declared for `vp dev`; never set it in production), `/auth/dev?login=octocat` signs in a fake user on loopback hosts. Options: `name`, `admin=1`, `allow=1` (add to the allowlist), `orgs=a,b` (pretend membership of allowlisted orgs), `return_to`. Dev users have negative ids.

## Security

The security review (#60) is in `docs/security-review.md`: what was checked, what was fixed, and what's left. What code has to keep doing:

- **Headers on everything**: the Worker's responses get them from `withSecurityHeaders` (nosniff, `X-Frame-Options: DENY`, a referrer policy, COOP, a permissions policy, HSTS over HTTPS, and a CSP: `default-src 'none'` for data, inline styles only for SVG, `same-origin` resources for `/api/` and `/auth/`). Pages the Worker serves (`/b/*`, for link previews) get the app's policy with the hashes of the inline scripts they actually have, so the dev server's page (which Vite rewrites) works too; a 304 carries no policy, so a cached page keeps its own. Static assets get theirs from `_headers`, which the build writes beside them (`securityHeaders()` in `vite.config.ts`) with the hash of `index.html`'s inline theme script. **The app's CSP**: scripts only from the app and by hash (no inline, no eval: never add either), styles inline (React Flow positions nodes with `style`), images from any HTTPS host, `data:` and `blob:`, fetches to the app, `wss:` (older Safari doesn't count the board's own WebSocket as `'self'`), `avatars.githubusercontent.com` and `github.com` (snapshots and exported images inline avatars), `base-uri 'self'` (modern-screenshot resolves the stylesheet's fonts with a `<base>`), forms to the app and GitHub (the app manifest), no framing. Something new the browser loads from elsewhere needs a directive here, and a check in the built app (`pnpm build && vp preview`) as well as the dev server.
- **Links from the document or the forge** go through `safeUrl` (`src/client/changes/inline.ts`): only http(s). Never `dangerouslySetInnerHTML` with anything that isn't ours.
- **Repository names** in keys must be plain path segments (`isRepoPath` in `src/shared/refs.ts`; `parseKey` and `parseRepoKey` refuse others), and paths built from anything else are encoded (`segments`), so nothing written into a board can point a request with someone's token at another API path.
- **Webhooks**: only the body is signed, so deliveries are told apart by its SHA-256 (`digestOf`) as well as their id (`Repo` keeps both for three days, installation events' digests for 30), an installation event only counts if its body is one, and comment commands written more than a week ago are ignored (`stale`).
- **Server-side fetches** only ever go to forge APIs at fixed hosts (`forgeFetch`): GitHub's, and the hosts in the instance's forge configuration (`config.ts`, #65), never one a board names that isn't configured; nothing fetches a URL someone typed.

## Public boards and embeds

Public boards (#56) are readable by anyone, signed out, read-only. What a signed-out visitor gets on every channel is only what anyone may see: cards from repositories not known to be public are bare placeholders (`visibleCard`), widget and inbox queries run at the `public` access level, related and search answer with public items only, the digest's card activity skips repositories they can't read, the push log is redacted (above), history and the document never hold card data, and `GET /api/boards/:id/people` gives them the board's members but not its recent visitors. `test/public-boards.test.ts` checks all of them against one public board with a private card on it. Board content itself (stickies, comments, staged changes' text) is public on a public board; silent mode's hidden text never reaches the document at all.

Embeds (#57) are drawn on the Worker, never in a browser, from what someone signed out would see:

- **Only public boards**, checked on every request with `Directory.publicBoard(id)`, which answers null for private and instance boards and for boards that don't exist alike: their images are the same `404`, and their pages the same plain app shell. Images use a strict anonymous view whatever the instance's setup state, so instance boards on an instance that isn't set up don't count as public.
- **Data**: `Board.embedData()` returns the board's shapes and its cards exactly as an anonymous connection gets them (`visibleTo(null, …)`), after waiting up to 2 s for a just-woken board's cards. `buildScene` (`src/shared/embed.ts`) is the only place deciding what's drawn, and draws nothing of a card that isn't `visibility: "public"`, whatever it's handed. Silent stickies are face down if they have any `silent` mark; widgets are frames and titles; comments, stamps, dots, votes, staged changes and authors aren't in the scene.
- **Rendering**: `draw.ts` turns the scene into Satori's element tree at the image's pixel size (text too small to read becomes bars, as zoomed-out boards do; titles of sections sit above them and grow as the board zooms out, up to 10×), Satori lays it out to SVG (text as paths, so it looks the same everywhere), and resvg makes PNGs. Both are WebAssembly modules imported as compiled modules (`.wasm`), and the fonts as data (`.bin`): Workers can't compile WebAssembly from bytes. **Satori is pinned to 0.32.0**: from 0.33 it loads HarfBuzz from a file at import time, which Workers can't do. The renderer is a dynamically imported chunk, so the Worker's start-up doesn't pay for it.
- **Caching**: the ETag is a hash of the scene, the options, the title and `RENDERER_VERSION` (bump it when drawing changes), so `If-None-Match` gets a `304` until what the image shows changes; drawn images go in the Cache API (`tack-embeds`) under that hash; `Cache-Control: public, max-age=60, stale-while-revalidate=600`. SVGs carry a `default-src 'none'` CSP.
- **Link previews**: `/b/*` runs the Worker first (`runWorkerFirst`); for a public board, the page from `ASSETS` gets its `<title>`, Open Graph and Twitter tags (`previewTags`), with `/og/:id.png?v={updatedAt}` as the image (1200 × 630, the board fitted above its title, `drawPreview`), and a description from `countBoard` naming only public repositories. Any other board's page is passed through untouched (bar the security headers, above).
- **Limits**: images are 240–2400 px wide and at most 2400 tall; areas at most 40,000 units a side; at most 900 shapes (the largest kept). Drawing takes a few hundred ms of CPU: more than the Workers Free plan's 10 ms, so on Free images may fail (`site/src/content/docs/self-hosting/costs.md` says so).

## Comment commands

Comment commands (#58) put an issue or pull request on a board from GitHub: `@tack add to roadmap`, `@tack add to roadmap in Next up`, `@tack help`. The app answers to its GitHub App slug (`@tack-example-com`) and to the aliases in `TACK_COMMAND_ALIAS` (a text binding in `cloudflare.config.ts`, comma-separated, empty by default, so only the slug works: a short alias like `tack` is a real GitHub login, which every command would notify).

- **Reading**: the app subscribes to `issue_comment`. The GitHub adapter only turns a comment into a delivery when it's a command (`findCommand`: a mention, then `add [to|on|onto] <board> [in|into <section>]` or `help`, outside quotes, code and HTML comments; other mentions are left alone). Comments by bots are never commands, the app's own replies included. An edited comment counts only if it held no command before the edit (`changes.body.from`). The delivery carries no card.
- **Once per comment**: the `Repo` remembers each command by comment id for 30 days, so redeliveries and edits never run it twice, and runs it from its alarm (the webhook answers at once), up to four tries a few seconds to minutes apart. The outcome is decided once; a retry only finishes answering, and a reply an unanswered attempt may have left is looked for before posting again.
- **Who**: the commenter's GitHub user id must be a Tack user's (they've signed in once) who is allowed on the instance, and the board one they can edit. Boards are matched among the ones they can open: by link or id exactly, else by title or slug (exact, prefix, words, substring, then a typo or two; ties are ambiguous). Archived boards are found only by link or exact name, to say they're archived; boards they can only view get "no permission", and boards they can't open aren't there at all.
- **Private repositories**: an item from a repository that isn't known to be public only goes on a private board with no outstanding invites whose members can all read the repository, each checked with their own token. That's stricter than pasting a link, on purpose: nobody on the board chose it, and its key alone names the repository and item.
- **Placing**: `Board.addFromCommand` places the card (`placeCommandCard`) in free space, with provenance `{ via: "comment", source: <comment URL>, by: <login> }`: into the named section (or just below it if it's full, as rules do), else below the last card a comment brought, else beside everything on the board. Items already on the board aren't added again. The change is credited to the commenter (a `CommandOrigin`), so "since you were here" shows it as theirs.
- **Answering**, as the app's bot: 👀 on the comment while it works, then a reply and 🚀 (done, already there, help) or 😕 (anything else) in place of 👀. GitHub has no ✅ reaction. Replies are public wherever the item is, so they never name a board or section that isn't public unless the commenter named it, and they quote what people wrote with mentions, links and Markdown defused (`quote`). Each repository posts at most 30 replies an hour (`command.limited` past that; reactions still say how it went).
- **Owners of apps set up before this** need to turn on the "Issue comment" event in the GitHub App's settings (Permissions & events → Subscribe to events). The permissions it needs (issues and pull requests, write) it already has.

## Silent mode

Silent mode (#49) keeps a section's new stickies' text from everyone but their author until it's revealed, and that's enforced by the server. A shared Yjs document can't keep a secret (every update goes to every connection, and Yjs can't filter updates per viewer), so hidden text never goes into the document at all:

- **Starting** is a `silent-start` request: an editor's, for a section. The server records a session in the board's SQLite and marks the section (`silent`, a `SilentSession`: id, who started it, when). Marks clients write themselves are put right (`SilentHub.reconcile`), so only the server starts and ends silent mode.
- **Writing**: a sticky made in a silent section (`addSticky` calls `joinSilentSession`) is marked with the session's id and has no `text` in the document. Its author's client claims it and sends what they type as `silent-text` (throttled; `setStickyText` is the one place sticky text is written, and it routes silent stickies there). The server keeps it per author (the first text for a sticky claims it; anyone else's is refused) and sends it back only to that author's connections: their other tabs, and on reconnecting (`silent-hello`). Everyone else sees the shape face down, with its author's name and colour and nothing more.
- **Revealing** is a `silent-reveal` request: the server writes every kept text into the document and clears the marks in one transaction (`SILENT_ORIGIN`, never undoable), so every sticky turns over at once, in a wave across the section.
- **Who can reveal**: whoever started the session, or the board's owner; once the facilitator has left the board, any editor, so a session is never stuck face down. Viewers can't start, write or reveal.
- What decides whether a sticky is face down is its own mark, set when it's made: dragged out of the section it stays face down; stickies that were there before, or dragged in, stay face up (everyone's seen them). A sticky a client made before hearing the section went silent is an ordinary one. Copies don't carry silent mode.
- Clients only ever learn others' hidden text from the document, at the reveal, so no client can expose anyone else's: it never has it. `test/facilitation-board.test.ts` checks that nothing another connection receives (messages, updates or awareness) contains it.

## History

History (#47) keeps the board's document over time in the board's own SQLite, compact and bounded, like a video: keyframes and deltas (`src/shared/history.ts` has the details). It's separate from since-you-were-here's `ChangeLog` (`src/server/since.ts`), which keeps only the latest change of each kind per shape, for digests; both watch the same document and flush with the same saves.

- **Steps**: every update to the document is recorded, attributed to who made it (the connection's person, or the server for pushes, rules, the reveal, the timer and repairs), and written as one step per person whenever the board saves (every 2–10 s), with a summary of the shapes it added, edited or removed (ids, types, the properties changed, where they were): never their text. A shape made and removed within one step leaves no trace.
- **Keyframes**: the whole document after some step, written whenever the steps since the last add up to more than the document (and at least 64 KB). The first step kept, the origin, always has one. Seeking loads the keyframe at or before a step and applies the steps after it; clients fetch a segment (keyframe to keyframe) at a time and keep it.
- **Thinning**: the last hour is kept as recorded, then merged into 5-minute steps for a day, hourly for a week, daily for three months and weekly after that. Merging replays the steps inside one transaction and keeps the update it emits, so deleted content is garbage-collected away. Every 10 minutes at most, as the board saves.
- **Budget**: past 8 MB of updates and keyframes, the oldest steps go: a later step becomes the origin, with a keyframe of its own. Clients learn earlier history changed from `generation`, and drop what they'd cached.
- **Restoring** is never rewriting history: shapes from the step shown come into the live board as your own edit (one undo step), with new ids, in place if they're gone, beside the originals if they're still there.
- **Access**: anyone who can open the board can read its history, as they can its document. Silent mode's hidden text never reaches the document before the reveal, so it never reaches history (`test/history-board.test.ts` checks every segment's bytes). Card data isn't in the document: replays show cards as they are now, and the panel says so.

## Compaction

A Yjs document keeps a tombstone for everything ever deleted, so it can merge with copies that saw it. Saves re-encode the state (deleted content goes), but tombstones stay: on a board used for years they can outweigh what's on it. Compaction (#60) rebuilds such a document with the same content and none of the history:

- **When**: only as a board's object loads (`BoardCompaction.load`, before anyone syncs), and only if the document is at least 256 KB, at least half tombstones, untouched for six hours (`saved_at`, kept with every save), not compacted in the last week, and the rebuild saves at least 30% (`COMPACTION_LIMITS`; `Board.compactionLimits` changes them for tests). Every load logs `board.document` (bytes, live items, tombstones, clients) whether or not it compacts.
- **Safely**: `rebuildDoc` copies every root into a fresh document and compares the two as JSON; if anything differs, nothing changes (`board.compact.failed`, reason `mismatch`). The rebuild, the old document's client ids (`retired_clients`) and a new `epoch` are written in one transaction.
- **Old copies**: a rebuilt document can't merge with the old one (every item's identity changed), so a connection whose state vector or updates name a retired client is closed with 4410 (`DOCUMENT_REBUILT`, logged as `board.document.stale`). The client drops the edits it was keeping for that board in every tab (`PendingEdits.discard`), reloads once, and says if any were lost.
- **History** starts a new stretch with a keyframe at the rebuild (`epoch` in the `HistoryLog`'s meta); thinning, seeking and replays never cross it.

## Format versions and migrations

Upgrades must never strand a board or an object's storage (#55). Both are versioned, and migrate themselves when they next load; there's never anything for an owner to run.

- **Board documents** carry their format's version in the root `meta` map (`schema`; absent is 0, boards from before versioning). `Board.onStart` runs `migrateBoard` (`src/shared/schema.ts`): every migration in `BOARD_MIGRATIONS` newer than the stamp, in order, each in its own transaction with `MIGRATE_ORIGIN` (never undoable) that also moves the stamp on; it saves straight after. A new board is stamped before history starts (so the stamp is part of its origin); an existing one migrates with history recording, which shows it as Tack's ("Tack upgraded the board"). A migration that throws is logged (`board.migrate.failed`), leaves the stamp where it was, and the board carries on; a board from a newer Tack (a rolled-back deploy) is left alone (`board.migrate.newer`). `Board.schemaReport()` says what loading did. Only the server writes `meta`.
- **Writing a board migration**: append it with the next version (never edit or reorder a released one), make it idempotent and write only what needs changing, never throw for malformed data, and keep readers tolerant of the old format for at least a release (a tab running old code writes the old way until it reloads, after the stamp has moved on). New _optional_ keys don't need one: readers default what's absent, as they always have. Version 1, `z-keys`, gives shapes from the spike stacking keys fractional-indexing can build on, keeping their drawn order. Test each against an old-format document (`test/schema.test.ts`), and the load path end to end (`test/board-schema.test.ts`). Template, export and import code that writes a document from JSON should stamp it (or run `migrateBoard` on it) too.
- **Durable Object SQLite**: tables are still created with `CREATE TABLE IF NOT EXISTS` every time each part starts, which is all a new table needs. Changing a table objects already have (a column, an index on one, rewriting rows) is a migration: `migrateSql(sql, scope, migrations)` in `src/server/migrations.ts`, one ordered list per part (`push` is the first, `PUSH_MIGRATIONS` in `src/server/push/migrations.ts`; `repo` is the `Repo`'s, `REPO_MIGRATIONS` in `src/server/repo.ts`), run once each and recorded in `schema_versions`. Add new columns to the `CREATE TABLE` too, use `addColumn` (idempotent: objects from before migrations were recorded run every migration once), and only ever add, so a rolled-back deploy still reads what a newer one wrote. Unit-test them over Node's SQLite (`test/sqlite.ts`'s `memorySql`, `test/migrations.test.ts`).

## Stacks and AI suggestions

Stacks (#73) are stickies gathered into one, as people theme a planning session: hold a dragged sticky over another and they become a stack, named by AI from what they say.

- **The shape**: a stack is its own lightweight shape (`type: "stack"`: x, y, z, parent, a person's `title`, the server's `suggested`), and membership is a key on each sticky (`stack`), as `parent` is for sections, so concurrent drops land and a drag out resolves whole. While in a stack, a sticky's x, y and parent are the stack's (`memberAt`); `commitMoves` writes them with `stack` when a stack moves. The stack's order is its stickies' z, top first. Containment, placement and repair need to know nothing else; lists and section counts skip stacked stickies (`isStacked`). A stack of one dissolves into its sticky and one of none goes (`settleStacks`, from deletes, drags out and repair). Opening a stack is this person's view (`stackStore.open`), never in the document.
- **Everything else**: deleting, copying, exporting, templates and thumbnails take a stack's stickies with it; a stack is one row in a list; it's votable and stampable; connectors to a stack that goes move to its top sticky; a stack whose stickies are about to become cards spreads out first (`makeRoomForCards`), so a parent issue from a stack (`ParentPanel`, `stageParentIssue` with the stack's stickies) lands as cards under their parent. Embeds draw its top three stickies peeking out, and its name.
- **Names**: `title` is a person's and nothing else writes it. `StackNamer` (one per board, on the server; the playground runs the same) watches the document and, `NAME_DEBOUNCE_MS` after a stack's visible text changes, writes a `suggested` name (`{ title, hash }`, as `STACK_ORIGIN`, never undoable) unless a person's named it, checking again after the answer comes back. The text is `namingTexts`: visible text only, never a face-down sticky's (which isn't in the document anyway), at most 40 stickies of 280 characters, sent as JSON data with a system prompt saying it's data. Names are cached by `stackHash` (order-independent) in the board's SQLite, failed text isn't asked about again for ten minutes, and each board spends at most 20 requests a minute and 240 an hour (Group these costs 4). Logged as `stack.named`, `stack.name.failed`, `stack.name.limited`, `stack.grouped`, `stack.group.failed`.
- **Group these**: `stack-group` with the selected ids; the server proposes stacks (short note ids `n1…` stand in for shapes, so the model never sees ours) back to that connection only, and the client previews them (`stackStore.proposal` rings and numbers the stickies) before `applyGrouping` makes them in one undo step. Names someone changed in the preview are theirs (`title`), the rest suggestions.
- **AI**: `src/server/ai.ts` is the only code that talks to Workers AI (`askModel`); keep other AI features' prompts and readers beside them, as `stackNaming.ts` does. `TACK_AI` (`cloudflare.config.ts`, a text binding) is on by default, `off` turns suggestions off, and without the `AI` binding they're unavailable; `/setup` shows which. Local dev has no binding (it'd reach the remote, billed service) and runs `TACK_AI=fake`, the stand-in in `fakeStackAi.ts`; `TACK_DEV_AI=workers-ai` asks the real thing. Tests run every Worker with a fake `AI` binding (`test/fake-ai.ts`, a service binding answering from Node), so they can see everything sent.

## AI on boards

AI on boards (#64): asking for a widget in words, summarising a selection, and drafting a decision from it, with Workers AI on the server (`src/server/ai/`, asking through `src/server/ai.ts` like stacks), part of the instance's AI suggestions. The rules:

- **Proposals only.** The route answers the person who asked and writes nothing, to the board or the forge. The client shows what came back to read and edit; placing it is their own edit (`transactLocal`, one undo step). A widget is only a config, whose queries run as whoever's looking like any widget's; a drafted decision is written back, if ever, through pending changes as any decision is.
- **What the model reads** is built on the server, from the board's document and the cards the asker may read (`BoardAi.prepare`), never from text the client sends (only shape ids, and a widget's description): face-down stickies aren't in the document, and cards from repositories the asker can't read (on a public board, any that aren't public) are left out, keys and repository names included; widget requests aren't told those repositories' names either. Board content is fenced as untrusted in the prompt. Prompts, content and answers are never logged.
- **Widgets are checked strictly** (`checkWidget`): a kind the registry has, every field accepted by its schema as given (a value its schema would replace with a default is a problem, not a default), and something to run; the model is asked once more with the problems, then the request fails as `unusable`. A new widget kind or field needs a line in `WIDGET_GUIDES`.
- **Previews**: `widget-preview` runs a proposed config's queries on the asker's connection, as them, with the runner's cache and budget, answered as `widget-data` for `widgetPreviewId(id)`.
- **Who and how much**: editors, while AI suggestions are on (`aiStatus`; clients hear it as `stacks-ai`, and `useAi` offers nothing until they do). With `TACK_AI=fake` (local dev) the stand-in in `src/shared/fakeBoardAi.ts` answers instead, keyword-made and still checked; the playground uses it too. Each board allows 12 requests a minute and 120 an hour, and each person 6 a minute (`AI_LIMITS`, in the `Board` object's memory; `boardStub(mf, id).aiLimits(...)` for tests). Answers time out after 30 s.
- **The model** is `AI_MODEL` (`src/server/ai.ts`), asked for JSON Schema structured output through `askModel`, with the conversation's later turns as `followUp` (`ask` in `src/server/ai/model.ts` adds a 30 s limit and reading the JSON: `parseAnswer` also reads it wrapped in text or a code fence).

## Lists and mini cards

A section can show what's in it as cards (free-form, as placed), as a list of compact rows, or as a grid of mini cards (#72). The design keeps the document renderer-independent and every shape a shape:

- **The document says only which mode, never where.** A section's `display` key (`list` or `mini`; absent is cards) and `sort` (`{ by: "state" | "number" | "title", desc? }`; absent is by hand), and each shape's `order` (a fractional index; absent sorts after those with one, in reading order, so a list first reads the way the cards were laid out). Shapes keep their free-form `x` and `y` while a list shows them, which is all "remembering each shape's position" takes: switching back puts everything where it was. Switching is one write, so it's one undo step, and undo, other people and the server's writes all animate the same way.
- **The layout is pure, and computed from the document alone** (`layoutDisplays` in `src/shared/display.ts`): rows and tiles have fixed sizes, a list is as wide as its section within limits (`LIST.minW`–`LIST.maxW`) and as tall as its contents, a grid fills its section's width with columns. Nothing is measured, so the server, every client and containment agree on where a list's rows are. Sections inside a list are groups: a header row, then their own contents, in their own mode or their list's.
- **Rows are the shapes' own React Flow nodes, repositioned and resized**, not something drawn inside the section node. `useDisplay` gives each shape in a list its slot; `Board` draws the node there at the slot's size with `data.display` saying `row`, `mini` or `group`, and `withDisplay` swaps the node's body for a row or mini card. So selection, the marquee, multi-select, connectors (which attach to the row's box, anchors and all), staged marks (`withStagedMarks` still wraps every node; compact on rows), the action bar, Expand related, keyboard focus and React Flow's culling all keep working unchanged. Rendering rows inside the section node instead would have hidden the shapes from all of that, and every one of those paths would have needed a second way to find a shape. Rows stack above any section lifted by selection (`LIST_ROW_Z`, `LIST_GROUP_Z`).
- **Measured sizes stay free-form.** React Flow's size for a row is the slot's, and is never written into `measured`, so `boxSize` (structural edits, placement, containment) only ever sees a shape's size as a card. `sizeOf` in `Board` is the drawn size, for UI around shapes.
- **Containment by what's drawn** (`sectionGeometries` in `src/shared/structure.ts`): a list takes what lands on the box it draws, wherever its free-form box is, counting as at least as big as its section so cards fit in a short list. Rows stay in their list on any re-parenting that isn't a drop of the row itself (their free-form positions say nothing about where they are), so moving, resizing or drawing sections around them never pulls them out. Whatever joins a list by geometry lands among the rows where it was dropped (unless the list is sorted), and gets a free spot in the section's free-form box and its `order` (`joinDisplay`); leaving a section forgets `order`. Placing into a section by name (a rule's section action, an inbox's tray clicked) uses `keepInSection`, since the spot found in the free-form box may be outside a short list.
- **Dragging** (`drop.ts`): while a shape is dragged over a list, `useDisplay` holds a gap open where it would land and the rows glide aside (no snapping for rows). On the drop, worked out again from where it was let go: a row dropped in its own list only gets a new `order` (no move is committed, so its free-form position is untouched); anything dropped on a list joins it at the gap (`placeInDisplay`, one undo step with the move); a row dropped anywhere else becomes itself again, centred where the row was let go. Moving a sorted list's own rows puts it back in order by hand, starting from what the sort showed, with a toast.
- **Keyboard** (`keys.ts`): arrow keys never nudge rows (that would move their hidden free-form positions); they move the selection to the nearest row or mini card that way, and Shift-arrows move what's selected up and down its list, or a line in a grid.
- **Motion**: rows glide (`display-node`), and a shape whose way of showing changes (`useMorphs`: cards to rows, rows to mini cards, a row pulled out) travels to its new place and unfolds into its new form, staggered down the list; the list's own height follows. Everything is scaled by `--motion`. Silent mode's reveal turns rows over in a wave down the list.
- **The pop-out** (`Preview.tsx`): a row's or mini card's full card (or sticky) after a moment's hover, at once when moving between rows, and pinned while it's selected alone, beside the usual action bar. It's drawn at screen size (a `NodeToolbar`), which is what makes a list readable zoomed out; rows and mini cards also drop to the state and a big title below 45%, and to bars of colour below 20%.
- **Silent mode** works as it does on stickies: a face-down sticky's row shows its author and nothing else (its text isn't in the document), yours show your own text marked as hidden, and a sticky made by clicking or dropping into a silent list joins the session as usual. Stamps and dot votes are counted inline on rows and mini cards rather than hung off them.
- **Not yet**: lists and grids can't be resized (switch to cards to resize: their width comes from the section's), connectors pass over rows rather than routing around them (the connector layer's one stacking context), and a grid's mini cards are all one size.

## Export, import and backups

Boards leave Tack as images or as their own JSON, and come back as new boards (#59):

- **Images** are drawn in the browser from the canvas's DOM (`src/client/export/`), so they look exactly like the board. Since React Flow only renders what's in view, and draws less detail zoomed out, drawing turns culling off and sets the zoom to 100% for a moment (`data-exporting` fades the canvas; `ViewPublisher` is paused so followers don't jump), then restores the view. SVG is the same DOM in a `foreignObject`: right in browsers, not in design tools. Server-rendered images (Satori and resvg) are the embeds issue's, not this.
- **JSON** is `tack.board`, `version` 1 (`src/shared/boardExport.ts`). It's the board's content, never people's own state: no comments, history, votes, dot votes, stamps, staged changes, provenance, inbox dismissals or face-down stickies, and cards the exporter can't read are left out (the client asks `cardStore` for private placeholders). Properties are copied by name per type (`KEEP`): a new shape property stays out of exports until it's added there. Change the format by bumping `BOARD_EXPORT_VERSION` and adding a migration from the one before.
- **Importing** makes a new board (`POST /api/boards/import`, up to 4 MB and 10,000 shapes): validated with Valibot on both sides, ids remapped, `z` regenerated in the file's order, invalid `order` keys dropped, decisions given fresh `votes` maps.
- **Backups** (`src/server/backups.ts`) commit the board's JSON to `boards/<id>.json` on a branch of a repository its owner chose, through the forge's `writeBranch` (GitHub's in `github-write.ts`: the git data API, an orphan commit the first time, fast-forward after, never the default branch, a retry if the branch moved), as the app. Only the owner turns them on, for a repository where the app's installed and they can write; before every backup `checkTarget` checks both again with the current owner's own token. Scheduled backups skip when nothing changed (a hash of the export without its time); a failure is kept and shown, retried sooner if the forge said to. Cards from repositories that aren't public are left out unless they're from the backup's own repository. The fake forge's `writeBranch` succeeds without a network (a branch with "fail" in its name is refused).

## Staged changes and pushing

What's staged follows the board, and each push is its pusher's own (docs/ux-review/writeback.md):

- **Staged issues follow their stickies.** An `issue.create` that replaces a sticky reads its title and body from the sticky until it's pushed (`followSticky` in `src/shared/changes.ts`; the push plan reads it too), and is marked `drift` (`edited`, `deleted`, `empty`) for the panel and sheet. Deleting a shape unstages what was made from it and what refers to that, in the same undo step. Words edited in the push sheet go back onto the sticky (`editStagedIssue`).
- **Inclusion is per push, not shared.** `PushSession.leftOut` is this person's choice in the push sheet; nothing about it is in the document. Changes to repositories without the app are left out by default, once each (`useUnwritableLeftOut`, `leaveOutByDefault`): a choice made by hand always wins.
- **Batches**: changes staged by one action share `batch` (in board reading order) and fold into one row in the panel (`batchRows`).
- **Marks on shapes** (`StagedMarks.tsx`): one mark per shape summing up everything on it, opening into a list on hover or focus, a dot below `MARK_DOT_ZOOM`; the ghost card behind a sticky shows only while it's pointed at, selected, picked out or being pushed. The action bar clears the marks when it sits above the selection.
- **Failures** are in plain words (`explain` in `github-write.ts`, worded for whoever pushed: you or the app); what GitHub said is kept as `errorDetail` (and `detail` in push history), behind Details (`ForgeError`). Failures with a `problem` offer a way out rather than a hopeless Retry (`FailureActions` in `parts.tsx`): **Move it here** for a sub-issue that already has a parent (`moveSubIssueHere`), **Leave it out**, and Retry only where it could work unchanged (`retryCanWork`).
- **After a push**: rows of stickies spread out so the wider cards fit (`makeRoomForCards` in `src/shared/swap.ts`, run as a push starts), and new issues can say where they came from (`src/shared/credit.ts`, a switch in the sheet, on by default).
- **The action bar** is a roving-tabindex toolbar: Tab from a selected shape or F6 reaches it; arrow keys inside any `[role=toolbar]` aren't board nudges (`commands.ts`). ⌘↵ stages from any `Popover` (its first enabled `.action-primary`). Unavailable actions are `aria-disabled` with their reason, not `disabled`.
- **Decisions**: what the write-back dialog edits lives on the decision (`text`, `outcome`, `consequences`; `setDecisionRecord`), written as people type. Records go in the folder the repository already uses (`ADR_DIRS`, `detectRecordDir`, `recordDir` in `adr.ts`), editable in the dialog and remembered per repository in the browser.
- **Backlink snapshots** are framed by `snapshotFrame.ts` (neighbours whole, even padding, section titles kept); the off-screen copy is at least the image's size.

## Load

`scripts/load-test.ts` puts many simulated people on one board (one `Board` object): each speaks the Yjs sync and awareness protocols as the app does, all moving their cursors at 5 Hz, ten of them moving shapes twice a second, on a board of 200 shapes. It reports connecting and first sync, how long an edit takes to reach everyone, messages per client and the server's memory. Run it against the built Worker in Miniflare (`pnpm build && node scripts/load-test.ts --worker --clients 200`) or a dev server (`node scripts/load-test.ts http://localhost:5173`).

Presence is most of a busy board's traffic and fans out to everyone, so the board relays it in batches every 40 ms (`AWARENESS_BATCH_MS` in `board.ts`): each connection gets at most 25 presence messages a second, however many people are moving. Results (2026-10-11, `--worker`, 20 s, on an 8-core Apple Silicon laptop that was also running the clients, so the server's share of the CPU was smaller than in production):

| People | Connect p50 / p95 | All synced | Edit seen by everyone p50 / p95 / max | Messages per client per second | Memory (workerd, peak) |
| ------ | ----------------- | ---------- | ------------------------------------- | ------------------------------ | ---------------------- |
| 50     | 37 / 52 ms        | 0.24 s     | 10 / 19 / 24 ms                       | 28                             | 186 MB                 |
| 100    | 114 / 142 ms      | 0.44 s     | 23 / 43 / 63 ms                       | 38                             | 246 MB                 |
| 200    | 317 / 415 ms      | 1.1 s      | 36 / 68 / 87 ms                       | 35                             | 359 MB                 |
| 400    | 508 / 824 ms      | 3.5 s      | 113 / 232 / 268 ms                    | 24                             | 502 MB                 |

No connection was dropped at any size, and 99% or more of edits reached every client within the run (the rest were made in its last moments). Up to about 200 people a board stays real-time; at 400 edits still land within a quarter of a second, but joining takes seconds. Memory is everything workerd holds (the Worker, every object, Miniflare itself; 85 MB idle), not one object's 128 MB limit. A Durable Object runs on one thread, so a board is the unit of scale, and its CPU (relaying, and applying edits) runs out long before connections do. Run it again after changing what the board sends per message or per connection.

- **Client errors**: the app is wrapped in an error boundary with an on-brand fallback, and on the board each shape, the connector, comment, inbox and marks layers, and each panel draw inside their own (`ShapeBoundary.tsx`): a shape that can't be drawn shows "This shape couldn’t be shown" with Try again and Delete in its place, a panel a pill saying so, and the rest of the board carries on. Both report like any render error (`source: "boundary"`). Render errors, `window.onerror` and unhandled rejections are posted to `POST /api/client-errors` (at most 10 distinct errors per page load), which accepts reports up to 16 KB from the app's own origin, rate limits per client IP (in memory, per isolate; the IP is never logged), and logs a `client.error` event with the message, stack, component stack, path (no query string) and user agent. No third-party service is involved.
- **Finding logs in production**: Workers Logs is enabled (`observability` in `cloudflare.config.ts`). In the Cloudflare dashboard, open Workers & Pages → `tack` → Observability, and filter on fields such as `event = client.error` or `level = error`. JSON fields are indexed automatically. From a terminal, `cf o11y telemetry query` runs the same queries against the Workers Observability API (see `cf schema o11y telemetry query` for the request body), and `cf o11y telemetry live-tail` prepares a live tail.
- **Finding logs locally**: the dev server prints log lines to the terminal, and also keeps them queryable through the Cloudflare local explorer: `curl -X POST http://localhost:5173/cdn-cgi/local/explorer/api/local/observability/query -H 'content-type: application/json' -d '{"sql":"SELECT ts_ms, level, message FROM logs ORDER BY ts_ms DESC LIMIT 20"}'` (use your dev server's port). The e2e tests use this to check that a crash on `/play/crash` lands as a `client.error` event.

## Development Workflow

- Uses **pnpm**, wrapped by **Vite+** (`vp`). Format and lint are oxfmt/oxlint via `vp check` — there is no prettier or eslint. Type checking runs inside `vp check` (tsgolint with `typeAware`/`typeCheck` enabled).
- Formatting uses tabs (configured in `vite.config.ts` under `fmt`).
- CI (test.yml) runs `vp check`, `vp test`, and `vp build` via the `voidzero-dev/setup-vp` action in the `test` job, and the Playwright smoke tests in a separate `e2e` job, with the browser cached by Playwright version.
