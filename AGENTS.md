This file provides guidance to agentic coding tools when working with code in this repository.

## Design principle: delight

The UI must be delightful, with FigJam as the bar: considered typography, micro-interactions, and lots of small details (how a card lifts when picked up, how a live update lands, how a push confirms). Treat polish as a feature, not a follow-up. Respect `prefers-reduced-motion`, and keep interactions at 60fps.

## Repository Structure

Tack: a GitHub-native collaborative whiteboard for open source planning, built as a Cloudflare Worker with Vite+ and the Cloudflare Vite plugin.

- `src/index.ts` — the Worker entrypoint: webhook route, partyserver routing, DO exports
- `src/server/board.ts` — `Board` Durable Object (one per board): Yjs document via y-partyserver, live card relay via custom messages, filtered per connection so private cards only reach viewers who can read them (`visibility.ts`), and watching its repositories while anyone's connected
- `src/server/repo.ts` — `Repo` Durable Object (one per repository, keyed by its id): card cache, board subscriptions, webhook log and fan-out, debounced CI refetches, reconcile on wake, repository status (`live`, `writable`, `visibility`), and ETag polling of repositories without the app while a board has them open (see `docs/github-data.md`)
- `src/server/routing.ts` — maps repository names to `Repo` objects by stable repository id, so renames don't split caches (see `docs/github-data.md`)
- `src/server/instance.ts` — `Instance` Durable Object (a singleton, `instance(env)`): the GitHub App's credentials, installations and their tokens, users, sessions and the access allowlist. Every credential is encrypted at rest with `TACK_SECRET`
- `src/server/directory.ts` — `Directory` Durable Object (a singleton, `directory(env)`): the board index. Boards (id, slug, title, owner, visibility, archived), members by GitHub login, visits ("Recent") and each board's thumbnail sketch. Separate from `Instance` so board traffic (a thumbnail update on every board save) stays off the session-lookup path
- `src/server/boards/` — board access (`access.ts`: `roleFor`, the one function deciding owner/editor/viewer from visibility and membership), the `/api/boards` routes and the per-board check on live connections (`routes.ts`), and thumbnail sketches (`thumbnail.ts`)
- `src/server/identity.ts` — the identity contract other code uses: `getViewer(request, env)` (HTTP and WebSocket upgrades), `viewerToken(env, viewer)` and `canUseInstance(env, viewer)`
- `src/server/auth/` — sign-in and sessions: `/auth/*` and `/api/me` routes (`routes.ts`), the GitHub OAuth flow with PKCE and refresh (`oauth.ts`), signed session cookies (`session.ts`), instance access checks (`access.ts`), and HKDF/AES-GCM/HMAC helpers (`crypto.ts`)
- `src/server/github/` — the GitHub App: manifest and RS256 app JWTs (`app.ts`), `/setup/*` and `/api/setup*` routes (`setup.ts`), webhook verification and installation events (`webhooks.ts`), and the token contract (`tokens.ts`: `repoToken`, `isInstalled`, `appJwt`) that everything reading GitHub goes through, plus the cron that redelivers failed webhooks (`redeliver.ts`)
- `src/server/forges/` — forge adapters (GitHub, plus a synthetic `fake.tack` forge for tests and stress boards): fetching items, verifying and normalising webhooks, capabilities, and writing (`apply`, `canWrite`, `repoMeta`, `listDirectory`; GitHub's are in `github-write.ts`), and reading for widgets (`search`, `related`, `release`; GitHub's search is in `github-search.ts`: GraphQL's `search` with a token, so results are full cards that say whether their repository is private, and anonymous REST issue search without one; once GitHub rate limits a token, that isolate stops searching with it until GitHub says). Everything outside this folder is forge-neutral. `apply` never throws for forge errors: they come back as results, rate limits retryable with `retryAt`, and `ApplyOptions.retryOf` makes creates look for what an unanswered earlier attempt made before making it again. The fake forge's writes succeed without a network (anything with `[fail]` in it is refused), sub-issues and blocked-by included, and its repositories count as writable without any app, so the whole push flow can be tried locally without GitHub. Items it creates are numbered from 100000 (even for issues, odd for pull requests), and their cards are open items of that kind
- `src/server/push/` — pushing staged changes (M2): the routes (`routes.ts`: `POST /api/boards/:id/push`, `GET /api/boards/:id/pushes`, `GET /api/repos/meta`, `GET /api/repos/files`), planning a push (`plan.ts`: checking operations from the document, dependency order, summaries), and the engine each `Board` runs (`engine.ts`). The engine snapshots what was pushed in the board's SQLite storage, applies it one write at a time from the board's alarm (a second apart, in batches, waiting out rate limits in order), writes statuses into the document with `PUSH_ORIGIN` (never undoable), confirms `sent` changes when the card shows them (`reflects` in `src/shared/confirm.ts`; the board subscribes to those items), reconciles ones that don't confirm in time, runs change effects (`replace`: shapes become the created item's card, in place; `place`: a card for the created item above the shapes it came from, connected to them, as a section's parent issue gets, `placeCard` in `src/shared/place.ts`, which slides it clear of other shapes as Expand related does), and keeps the audit log. SQLite is the truth: a change being pushed or applied is never pushed again, whatever the document says
- `src/server/related.ts` — `GET /api/boards/:id/related?key=…` (M3, #42): what's related to an item (parent, sub-issues, blocked-by, blocking, linked pull requests; `related` on the forge adapter, in `github-related.ts` for GitHub along with `release`), for anyone who can open the board, as they may see it: asked with their own token, and anything from a repository that isn't public that they can't read is left out entirely, keys and all
- `src/server/rules.ts` — the rules engine (#44): each `Board` runs its rules (`src/shared/rules.ts`) on every webhook delivery it hears about (`Board.repoActivity`, called by `Repo` for every board subscribed to any of its items, or watching it for an inbox, with the delivery's items under each board's keys and what a pull request's text mentions or closes, `Delivery.mentions`). Rules run with the app's access (the delivery's data) and only place items from repositories already on the board; they write with `RULE_ORIGIN` (never undoable), and which items each rule has placed is kept in the board's SQLite (`rule_placed`), so a rule never places an item twice, even after someone removes it. The same pass keeps "no longer matches" marks (`unmatched`, see `provenance.ts`) current for cards an inbox or a matching rule brought, from the delivery's data (`refreshMatches`); an inbox's results only ever clear marks (`confirmMatches`), since one viewer's results leaving a card out may just mean they can't read it
- `src/server/widgets/runner.ts` — the widget runner (#37), one per `Board`: it runs the queries of every widget (`widgetQueries` from the registry) and inbox section (one query named `inbox`, #40) that a connection watches (`widget-watch`/`widget-unwatch`/`widget-refresh` with shape ids; `inbox-preview` for an inbox editor's live count, answered under `previewId(section)`), and sends `widget-data` keyed by the shape's id. Queries run with the permissions of the person on the connection: access level `user:{id}` searches with their own token (and `@me` is them, from `ConnectionAccess.login`); everyone else is `public`, whose searches get `is:public` added, run with any signed-in reader's token for the rate limit, and drop any result not known to be public (`@me` is an error). Results are cached per query and access level, so two tabs (or two widgets with the same search) cost one search. They refresh when a delivery reaches the board from a repository a query names, or its results came from, or for queries that search everywhere (`Board.repoActivity`, debounced, at most every 10 s), on the definition's `refresh` schedule (inboxes every minute), and on request (throttled). A per-access budget keeps searches well inside the forge's search limits, rate limits are waited out (`retryAt`), and a refresh that fails keeps the last good result, which the client shows as stale. Inbox results confirm the cards an inbox brought (`confirmMatches`). `related` and `release` queries run through the adapters too, keeping only public items (and items from public repositories) for viewers without a token. Definitions work out their queries from their config and a `QueryContext` (the time, for relative ranges; the cards in a section, for kinds that say `readsBoard`, read again when cards move between sections), and may ask for `followUps` from their first results (a dependency map's `related` per search result, at most `MAX_FOLLOW_UPS`), which run with the same caching and arrive in the same message. Searches and other reads have separate per-minute budgets. Boards watch the repositories their queries read with `Repo.watch`, so `Repo`'s activity fan-out reaches them
- `src/server/comments.ts` — comments on the server (#51): `CommentsService` keeps threads and messages in the board object's SQLite storage (not the document: viewers can comment but can't write it, the server stamps who wrote each message, and read state is private; see `src/shared/comments.ts`), checks every `comment-*` request from a connection (rate limited per connection), and the board sends the whole thread to everyone connected. Viewers who are signed in can comment, reply, and resolve or move their own threads; editors and owners can resolve and move anyone's; people edit and delete only their own messages, and owners can delete anyone's (deleted messages can be restored by their author for ten minutes, for Undo). Signed-out visitors to public boards read comments but can't write them, and archived boards are read-only for everyone. Mentions are checked against the board's people (`Directory.mentionable`: members, and people who've opened it lately) and notify them, as replies notify the others in a thread, through `Directory.notify`. Pins on a shape keep their resting point in step with it (`shapeMoved`), so they stay where it was if it's deleted. Read state is per person (`comment_reads`), sent only to their own connections
- `src/server/since.ts` — since you were here (#46) on the server: `ChangeLog` watches the document and keeps one row per shape and kind of change (added, moved, changed, removed: the latest, with who, from the transaction's origin: a connection, a rule or a push; repairs aren't anyone's), buffered and flushed with saves; `CardHistory` keeps a dozen snapshots per card (state, comments, CI, review) whenever one changes; `Visits` remembers each signed-in person's first visit, when they were last here (on leaving, and every minute while here) and the visit their digest is since, a new visit starting after 15 minutes away (`VISIT_GAP_MS`), so reloads keep the digest. The board answers `since-request` with a `Digest` of other people's edits, card activity (only for repositories the viewer can read) and pushes since then, and `since-seen` ("Mark all as seen") starts again from now. Signed-out people send the time their browser remembers
- `src/server/notifications.ts` — `GET /api/notifications` and `POST /api/notifications/read`: the top bar's inbox of mentions and replies, kept by the `Directory` per person (their latest 200), from boards they can still open
- `src/server/facilitation.ts` — facilitation on the board's server (M4, #50 and #49): `Facilitation` answers `clock` pings with the server's time, writes the shared timer into the document in the server's clock (`timer` requests, editors only), holds spotlight in memory tied to the spotlighter's connection (editors only; it ends when they leave, and latecomers are told on connect), and runs silent mode's `SilentHub` (`src/shared/silentHub.ts`) over the board's SQLite (`silent_sessions`, `silent_texts`). Each connection's requests are handled in order. Who someone is, for owning hidden text, is their GitHub user id, or for a guest the SHA-256 of a random secret their browser keeps (`silent-hello`; at least 16 characters, else just the connection)
- `src/server/webhooks.ts` — `POST /webhooks/:forge` routing
- `src/server/log.ts` — structured logger: one JSON line per event (see Observability)
- `src/server/clientErrors.ts` — `POST /api/client-errors`: browser error reports, logged as `client.error` events
- `src/server/snapshots.ts` — board snapshots for backlink comments that ask for one: `POST /api/boards/:id/snapshots` (a PNG body, editors only, at most 1.5 MB and 4096px a side, 1000 per board) returns `{ url }`, and `GET /snapshots/:id.png` serves it publicly with a year's `immutable` caching (GitHub's image proxy fetches it). The id is the board object's id (which says nothing about the board) then 128 random bits, so serving an image never touches the board index, and only reads the snapshot table, never the board's document. Images live in the `Board` object's SQLite storage
- `src/shared/` — forge-neutral item keys (`{host}/{repo}{#|!}{n}`, see `refs.ts`), card types and the Yjs shape schema (`shapes.ts`, documented there), used by both server and client. Pure canvas logic lives here too, so it's unit-tested in Node and usable on the server: `geometry.ts`, `sections.ts` (containment), `connectors.ts` (ends and routing), `structure.ts` (structural edits), `repair.ts` (the repair pass for dangling references), `decisions.ts` (decision edits: votes in a nested Y.Map keyed by voter, status, linked items, the write-back), `adr.ts` (the pure ADR template, record numbering and the write-back operations), `provenance.ts` and `related.ts` (below), `widgetRegistry.ts` (the widget registry: each kind's `WidgetDefinition`, configs read through its Valibot schema field by field with defaults, the list widget, `addWidget`, `queryScope`) the widget kinds' own pure logic: `timeline.ts` (ranges, the search with its date qualifier, ticks, stacking and clusters, density), `releaseDraft.ts` (sections by label, contributors, the next version, Markdown notes) and `dependencyMap.ts` (the blocked-by graph, cycles, layered layout, critical path, and planning it onto the board as cards and `blocks` connectors), and the review queue, milestone and stale finder (`review.ts`: a pull request's wait, size and review standing, oldest first; `milestone.ts`: progress, the burn-up from items' `createdAt` and `closedAt`, pace and forecast, due dates and what's at risk; `stale.ts`: the search with its `updated:<` cutoff, groups by how long items have been quiet, and the ping comment), with `widgetContext.ts` (`boardQueryContext`: what a widget's queries may read from the board), and `search.ts` (the one reading of GitHub-style searches, for widgets, the fake forges, rules and inboxes: parsing into terms, `searchScope`, `matchSearch` yes/no/unknown, its local reading for rules and inboxes, `matchesQuery(card, query)`, true, false, or null when the card can't answer, e.g. `milestone:` or `@me`, with words decided by the title, and `unsupportedForRules`; and `planMatch`, the label, assignee, milestone and state changes that would make a card match a search, or why none can, for drop to match). For M3's automation: `mentions.ts` (references and closing keywords in a pull request's text), `placement.ts` (free space beside a shape or inside a section: never over a shape, across a section's edge or over its title), `inbox.ts` (inbox frames: `inbox` and a nested `dismissed` Y.Map on sections, the tray, sorting a match out with provenance `inbox`, and whether a card still matches) and `rules.ts` (the `rules` Y.Map, the `ruleLog` Y.Array, describing rules in words, and `runRules`, which the server and the playground both use)
- `src/shared/facilitation.ts` — facilitation (M4, #50): the shared timer (`Timer` under `timer` in the document's `facilitation` map; `applyTimer` is the one place it changes, given the server's clock), `clockOffset` (the client's estimate of the server's clock, from the ping with the shortest round trip), spotlight's shape, stamps (the root `stamps` map: one key per person, shape and stamp, so they merge and need no nested map someone could be creating concurrently; `toggleStamp`, `stampCounts`) and emotes and high-fives (awareness only: `emote` with a counter so repeats float, `highFive` while a hand is held out; `highFives` pairs raised hands that meet, deterministically, so everyone watching sees the same high-five)
- `src/shared/silent.ts`, `src/shared/silentHub.ts` — silent mode (M4, #49), see "Silent mode" below: the section's session mark, `joinSilentSession` (a new sticky in a silent section is marked and has no text in the document), face-down counts, and the server's half (`SilentHub`: start, per-author text, reveal, and keeping sections' marks in step with the sessions it holds), written once for the Durable Object and the playground
- `src/shared/dotvotes.ts` — dot voting (M4, #48): votes in the root `dotVotes` map with their settings and a nested `ballots` map (made with the vote) keyed by voter (`voterKey`), each ballot replaced whole by its voter; a vote covers a section (however deeply nested) or the board, and a shape's dots go to the innermost open vote around it; open until closed or until `endsAt` (a window that can last days), reopenable; `tallyVote` ranks shapes, ties sharing a rank, and with `reactions` counts 👍 on a card's item (`Card.thumbsUp`) as votes, less those of people who also put a dot on that card here (`reactionVotes`, by GitHub login). GitHub's GraphQL fetch says who reacted (`thumbsUp: reactions(content: THUMBS_UP)`); REST and webhook payloads only count, so `Repo` keeps who from the last full fetch (`keepDetails`). GitHub sends no webhook for a reaction, so they arrive with the card's next fetch `hidden` keeps others' dots out of sight until it closes: a courtesy, not a secret (ballots are in the document)
- `src/shared/provenance.ts` — provenance (M3, #41): how each card arrived (`Provenance`: manual, list, inbox or rule) and what happens when it stops matching. **Every card is made through `addCardShape` (or the client's `addCard`, which takes the same optional provenance)**. Manual is the default and is never stored: a card without `provenance` was placed by a person, which includes pasting or typing a link, Expand related and copies of other cards (paste and duplicate drop `provenance` and `unmatched`, `CARD_UNCOPIED`). `whenUnmatched` decides: manual and list cards stay as they are (a list only ever copies), inbox and rule cards are marked. Whatever runs an inbox's or rule's query calls `updateMatches(doc, source, matches, { origin })`, which sets or clears the card's `unmatched` key (when it stopped matching) and never removes or moves a card; people then keep it (`keepCard`: it becomes manual, so it's never marked again) or remove it. `provenanceSourceName` and `describeProvenance` say where a card came from (a list widget's `config.title`, an inbox section's title, a rule's `name` in the document's `rules` map)
- `src/shared/related.ts` — Expand related's layout (#42), pure: `planExpand` puts the parent (or a pull request's closing issues) above, sub-issues below in rows of four, blocked-by to the left, blocking to the right and linked pull requests above those, each group sliding outward (and a little sideways) to the nearest spot clear of every other shape; items already on the board are connected where they are, and pairs already connected aren't connected again. `applyExpand` writes the plan (call inside `transactLocal`: one undo step). Connectors: hierarchy as elbows parent to child, `blocks` in red from blocker to blocked (as blocked-by staging reads them), pull requests dashed purple (`closes` when they do)
- `src/shared/comments.ts` — comment threads (#51), pure: the thread, message and anchor types, the requests and events on the board's connection (`CommentRequest`, `CommentEvent`), mentions (`mentionedLogins`, `validMentions`, `bodyParts`, and `mentionAt`/`completeMention` for the composer), unread (`isUnread`: a message from someone else since you last read it, or since your first visit), the panel's filters, and pins (`pinPosition` follows a shape, kept inside it; `anchorAt`)
- `src/shared/since.ts` — since you were here (#46), pure: the `Digest`, what a transaction did to shapes (`shapeChanges`), what happened to a card between snapshots (`cardActivity`), highlights (`highlightsFor`: one per shape, closed beats new beats changed beats moved), edits in words ("added 2 stickies and 1 section, moved 1 card") and new comments since a visit (`commentDigest`)
- `src/client/` — React + React Flow canvas (own `tsconfig.json` with DOM types); `index.html` at the repo root is its entry
- `src/client/undo.ts` — undo and redo with `Y.UndoManager`, tracking only this client's changes. **Every local document write must go through `transactLocal(doc, fn)`** (origin `LOCAL_ORIGIN`, `"local"`), or it can't be undone; changes from other people, the server and seeding are never undone. One transaction is one undo step
- `src/client/sections.tsx`, `src/client/connectors.tsx`, `src/client/canvasStructure.ts` — sections (React Flow nodes, containment through a stored `parent` key) and connectors (our own SVG layer inside the viewport); see `docs/react-flow-probe.md`
- `src/client/Minimap.tsx` — the minimap, which steps aside (fades and lets the pointer through) while the pointer reaches for something under it, a drag comes near it, or a selected shape, toolbar or popover overlaps it (#71). Popovers keep clear of the chrome fixed over the canvas (`CHROME` in `src/client/actions/Popover.tsx`: React Flow's panels, the tool dock and anything marked `data-chrome`; placed by `popoverPlacement.ts`, unit-tested), so mark any new panel that floats over the canvas with `data-chrome`
- `src/client/widgets/` — widgets on the board (#37, #38, #39): the widget node (`WidgetNode.tsx`: sized by the shape's `w` and `h`, picked up by its header, resized from the shared section grips when selected, its config panel beside it in a `NodeToolbar`), the board-free list view the gallery also uses (`ListView.tsx`: every state, rows that slide in, fold away and flash, the on-board pin, and the drop-to-match overlay), config panels (`ConfigPanel.tsx`: written for the list, generated from the schema for other kinds), the picker (the widget tool, W), dragging rows out as cards (`RowDrag.tsx`: a ghost at the board's zoom, made with `addCardShape` and provenance `{ via: "list", source }`), drop to match (`useDropToMatch.ts` catches card drops on lists, which glide back; `match.ts` plans and stages through `stageTriage` as one undo step; `DropConfirm.tsx`), the timeline, release draft and dependency map (`kinds.tsx` on the board; board-free views `TimelineView.tsx`, `ReleaseView.tsx` and `DependencyView.tsx`; their panels in `panels.tsx`; the frame, footer, empty and error states, skeleton rows and zoomed-out summary widgets share in `chrome.tsx`), the review queue, milestone and stale finder (`ReviewView.tsx`; `MilestoneView.tsx` with its progress ring and scrubbable burn-up; `StaleView.tsx` with quick actions that stage through `stageTriage` and `stageComments`, shown on the row with undo; each board-free for the gallery, with their nodes in `KindNodes.tsx`, panels in `KindPanels.tsx` and styles in `kinds.css`; below cards' compact zoom each draws one big number instead), what those nodes share (`host.tsx`: `useWidgetHost` reads the config, data, status and refreshing, `useRows` makes rows drag out as cards and light up with theirs, `useCompact`; `rows.tsx`: `useRowMotion` and `ItemRow`), and the data store (`store.ts`: `widget-data` by widget id, watched while mounted and for a few seconds after, through a swappable transport; the linked-highlight store between rows and cards; which items have cards on the board)
- `src/client/decisions/` — the decision node (`DecisionNode.tsx`, with the board-free `DecisionView.tsx` the gallery uses) and the write-back dialog, which stages an ADR pull request or a Discussion post as a pending change. Its repository endpoints go through the swappable `repoApi` (in `src/client/changes/api.ts`), which the playground fakes. A written-back decision stores its pull request as `ref`, so the board follows its live state like a card's
- `src/client/commands.ts` — keyboard shortcuts, clipboard, nudging and arranging; `shortcuts.ts` is the single list behind both the key handling and the `?` sheet. Shortcuts ignore keys typed into text fields. Clipboard and snapping (`clipboard.ts`, `snapping.ts`, `arrange.ts`) are generic over shape types: copy carries every property, and snapping uses measured bounds
- `src/client/boards/` — the home page (`/`), board routes (`/b/{id}/{slug}`, and `/?board=name` redirects), the renameable title, the share dialog, tiles and SVG thumbnails
- `src/client/changes/` — pending changes and pushing (M2): the push API client other code reuses (`api.ts`: `pushApi(boardId)`, a shared `RepoMetaCache`), the store over the document's `changes` map with stable per-shape snapshots (`store.ts`), how changes read, group, depend on each other and who they notify (`describe.ts`, pure), staging edits that keep dependencies whole and the push in progress (`session.ts`), and the UI: the top bar's Changes button, the panel, marks on shapes (`withStagedMarks` wraps every node type) and the push sheet with review, progress and history. Its previews render Markdown as React elements, never HTML (`Markdown.tsx`; inline Markdown, links and linked images included, is parsed in `inline.ts`, unit-tested, keeping only http(s) URLs). Statuses arrive through the document, never by polling
- `src/client/auth/` — sign-in UI: the `/api/me` store (`me.ts`), the account menu, the access gate with the sign-in and "invite-only" pages, and the `/setup` page
- `src/client/actions/` — the selection actions (M2, #32 and #33): a bar under the selection (`ActionBar.tsx`) that stages stickies as issues (optionally starting with labels, a milestone and assignees, picked in the panel and written with the create), a section or cluster as a parent issue with sub-issues, and triage (labels, milestone, assignees, close/reopen) and backlinks on cards; blocked-by from a connector's toolbar (`BlockedBy.tsx`). Every action only stages pending changes (staging logic in `src/shared/actions.ts`, unit-tested), one undo step each, and offers only the writes the forge supports (`RepoMeta.writes`). Pickers (`pickers.tsx`) are keyboard-first; shortcuts are ⌥I, ⌥⇧I, ⌥L, ⌥M, ⌥P, ⌥C, ⌥B and ⌥K. Expand related (⌥E, `ExpandRelated.tsx`, M3) is the one action that doesn't stage anything: on a single card it fetches what's related through `WriteServices.related` (the board's related route), lets you switch groups off (a little compass shows where each goes), and lays them out, flying out from the card in turn (`src/client/entering.ts` choreographs entrances for shapes added together) while their connectors draw in; the view pans to show them if they're off screen. A backlink is a link to the board (and the section the card's in, if any); a snapshot of the board is opt-in, a switch in the panel that's off by default and remembered per board (localStorage), and nothing is drawn or uploaded unless it's on. Snapshots are drawn in the browser with modern-screenshot (`snapshot.ts`) from an off-screen copy of the canvas DOM at rest (no selection, hover, staged marks, toolbars, cursors or minimap, animations off), one per audience: cards from other private repositories are replaced by a placeholder before the image is made (`src/shared/backlinks.ts`). `services.ts` is what they need from outside the document (repository metadata, snapshot uploads); the playground passes in fakes
- `src/client/inbox/` — inbox frames (#40): the tray on an inbox section's right edge (`InboxTray.tsx`, drawn in a `ViewportPortal` above every shape, growing against the zoom like section titles), where new matches wait marked new to be dragged out (a ghost card follows the pointer; it lands as a card with provenance `inbox`), clicked into the section, or dismissed (with Undo); the query editor with a live count (`InboxEditor.tsx`); and the store of results from `widget-data` (`store.ts`, reference-counted watching, wired to the live connection or the playground's simulation). "Make inbox" is on a section selected on its own
- `src/client/rules/` — the rules panel (#44), from the top bar's Rules button: rules in words with a switch to pause each and what it has done, a composer for the two kinds (linked pull requests beside their issue; matching items into a section, with the query checked as you type), recent activity ("Placed #431 beside #412, 2 min ago"; click to go to the card), and a toast when a rule places a card while you watch
- `src/client/comments/` — comments (#51) on the canvas: the store over the board's `comment*` messages (`store.ts`, optimistic: a write shows at once and the server's thread replaces it), pins (`CommentLayer.tsx`, in a `ViewportPortal` above every shape, following their shape live as it's dragged and the same size on screen at any zoom; hovering one opens a preview, and people who can move it can drag it) and the thread popover, the comment tool (B, for bubble: click anything to comment on it, or anywhere), the composer with @mention suggestions (`Composer.tsx`, people from `GET /api/boards/:id/people` via `people.ts`), the board-free thread (`Thread.tsx`), the Comments panel and top bar button (`CommentsPanel.tsx`: open, resolved, mentions), and the notifications bell (`Notifications.tsx`; `#comment=…` links open a thread). Signed-in viewers get a view-only toolbar with the comment tool

## Configuration Architecture

- **`cloudflare.config.ts` is the source of truth for the Worker**: name, entrypoint, compatibility, bindings, observability. It uses `defineConfig({ worker: { ... } })` from `cf/config`, which both the `cf` CLI and the Vite plugin read.
- The entrypoint uses the `with { type: "cf-worker" }` import attribute. This is what makes `Env` and `exports` inference work — keep that form when changing the entrypoint.
- **Previews**: `cloudflare.config.ts` uses the function form of `defineConfig`, which receives `isPreview`. Previews don't inherit production settings, so it returns the complete config for both. Previews get no secrets (webhooks only go to production, and card fetches work unauthenticated), so the code must treat `GITHUB_WEBHOOK_SECRET`, `GITHUB_TOKEN` and `TACK_SECRET` as optional.
- **Bindings**: declare them in `cloudflare.config.ts` (e.g. `env: { MY_KV: bindings.kv() }` with `bindings` from the same import). The `Env` type is inferred from them — run `pnpm types` after config changes. Durable Object bindings to this same Worker are untyped; `src/server/namespaces.ts` restores the class types. Integration tests declare the same bindings for Miniflare in `test/harness.ts`, so keep the two in step.
- **`compatibility.ts`** exists so the test runtime (`test/harness.ts`) always matches the deployed runtime. Extra exports are not allowed in `cloudflare.config.ts` (its exports are schema-validated), which is why this is a separate file.
- **Version pins that must move together**: the `vite@*` and `vitest@*` overrides in `pnpm-workspace.yaml` pin Vite to `@voidzero-dev/vite-plus-core` at the installed `vite-plus` version, and Vitest to the version `vp toolchain vitest` reports. Update them whenever `vite-plus` changes. There are no direct `vite` or `vitest` dependencies: import test APIs from `vite-plus/test`.

## Auth and access

- **Secrets**: `TACK_SECRET` signs session cookies and encrypts stored credentials (keys derived with HKDF). Without it (Previews), sign-in and setup are off, `getViewer` returns null, and boards work anonymously. Code must keep working that way.
- **GitHub App**: created from a manifest at `/setup`; `/setup/callback` stores its credentials in `Instance`, and whoever completed setup becomes the first admin. Webhooks verify against the stored webhook secret, then `GITHUB_WEBHOOK_SECRET`. Installation tokens are minted with an app JWT, cached, and refreshed five minutes before expiry; repos map to installations from `installation`/`installation_repositories` events, or a lookup on a miss.
- **Sign-in**: the GitHub App's OAuth flow (state and PKCE) via `/auth/signin` → `/auth/callback`. Sessions are a random id in a signed, HTTP-only, SameSite=Lax cookie (Secure over HTTPS); only its hash is stored. User tokens are stored encrypted and refreshed (with rotation) by `viewerToken`.
- **Access**: once the app is set up, only admins, allowed users and members of allowed orgs (checked at sign-in) may use the instance; `canUseInstance(env, viewer)` says whether a viewer may. Before setup everything is open.
- **Boards**: each board has an owner, members (owner, editor, viewer; invited by GitHub login, resolved to an id when they first show up) and a visibility: private (members only), instance (anyone allowed on the instance, at the board's `instanceRole`) or public (also anyone at all, read-only, signed out). Membership needs instance access too; only public boards reach past the allowlist. Archived boards are read-only. `roleFor` in `src/server/boards/access.ts` decides. Live connections are checked per board in the Worker (`authorizeBoardConnection`), which passes the role to the `Board` object in a header it always overwrites; viewers get read-only connections (`isReadOnly`), and role changes reach open connections straight away (or close them with code 4403). Board membership never grants access to repo data: per-viewer card filtering (#10) goes in `Board.visibleCards`. The access header also carries whether the board is archived and, for signed-in people, their login, name and avatar (URI-encoded, as names needn't be Latin-1), for attributing comments and edits. Comments are the one thing viewers can write: see `src/server/comments.ts`. Boards from before the index (`?board=name`) are adopted with their old name as id, so their documents carry over.
- **Dev sign-in**: with `TACK_DEV_AUTH=1` in `.dev.vars` (only declared for `vp dev`; never set it in production), `/auth/dev?login=octocat` signs in a fake user on loopback hosts. Options: `name`, `admin=1`, `allow=1` (add to the allowlist), `orgs=a,b` (pretend membership of allowlisted orgs), `return_to`. Dev users have negative ids.

## Silent mode

Silent mode (#49) keeps a section's new stickies' text from everyone but their author until it's revealed, and that's enforced by the server. A shared Yjs document can't keep a secret (every update goes to every connection, and Yjs can't filter updates per viewer), so hidden text never goes into the document at all:

- **Starting** is a `silent-start` request: an editor's, for a section. The server records a session in the board's SQLite and marks the section (`silent`, a `SilentSession`: id, who started it, when). Marks clients write themselves are put right (`SilentHub.reconcile`), so only the server starts and ends silent mode.
- **Writing**: a sticky made in a silent section (`addSticky` calls `joinSilentSession`) is marked with the session's id and has no `text` in the document. Its author's client claims it and sends what they type as `silent-text` (throttled; `setStickyText` is the one place sticky text is written, and it routes silent stickies there). The server keeps it per author (the first text for a sticky claims it; anyone else's is refused) and sends it back only to that author's connections: their other tabs, and on reconnecting (`silent-hello`). Everyone else sees the shape face down, with its author's name and colour and nothing more.
- **Revealing** is a `silent-reveal` request: the server writes every kept text into the document and clears the marks in one transaction (`SILENT_ORIGIN`, never undoable), so every sticky turns over at once, in a wave across the section.
- **Who can reveal**: whoever started the session, or the board's owner; once the facilitator has left the board, any editor, so a session is never stuck face down. Viewers can't start, write or reveal.
- What decides whether a sticky is face down is its own mark, set when it's made: dragged out of the section it stays face down; stickies that were there before, or dragged in, stay face up (everyone's seen them). A sticky a client made before hearing the section went silent is an ordinary one. Copies don't carry silent mode.
- Clients only ever learn others' hidden text from the document, at the reveal, so no client can expose anyone else's: it never has it. `test/facilitation-board.test.ts` checks that nothing another connection receives (messages, updates or awareness) contains it.

- **Client errors**: the app is wrapped in an error boundary with an on-brand fallback. Render errors, `window.onerror` and unhandled rejections are posted to `POST /api/client-errors` (at most 10 distinct errors per page load), which accepts reports up to 16 KB from the app's own origin, rate limits per client IP (in memory, per isolate; the IP is never logged), and logs a `client.error` event with the message, stack, component stack, path (no query string) and user agent. No third-party service is involved.
- **Finding logs in production**: Workers Logs is enabled (`observability` in `cloudflare.config.ts`). In the Cloudflare dashboard, open Workers & Pages → `tack` → Observability, and filter on fields such as `event = client.error` or `level = error`. JSON fields are indexed automatically. From a terminal, `cf o11y telemetry query` runs the same queries against the Workers Observability API (see `cf schema o11y telemetry query` for the request body), and `cf o11y telemetry live-tail` prepares a live tail.
- **Finding logs locally**: the dev server prints log lines to the terminal, and also keeps them queryable through the Cloudflare local explorer: `curl -X POST http://localhost:5173/cdn-cgi/local/explorer/api/local/observability/query -H 'content-type: application/json' -d '{"sql":"SELECT ts_ms, level, message FROM logs ORDER BY ts_ms DESC LIMIT 20"}'` (use your dev server's port). The e2e tests use this to check that a crash on `/play/crash` lands as a `client.error` event.
