# Security review

The security review (#60, M5): what was checked, what was found and fixed, how it's kept fixed, and what's left. Who may use each route and board message is the access table in AGENTS.md ("Access table"); what code has to keep doing is AGENTS.md's "Security".

## What was checked

- **Every route and board message**, for who may use it: a table of them all (AGENTS.md), checked by `test/access-table.test.ts` with seven kinds of people, from a stranger to an admin.
- **Headers**: what every response the Worker and the static assets send, and whether the app, the dev server, embeds, link previews, GitHub avatars, backlink snapshots and exported images still work under the policy, in a browser, on both the dev server and the built app (`vp preview`, which applies `_headers` as production does).
- **Cross-site requests** (CSRF and cross-site WebSockets), cookies and sessions, sign-in redirects.
- **Content from other people** wherever it's rendered: the document (any editor writes it), card data from the forge, comments, presence, Markdown in previews, the embed renderer and link preview tags.
- **Webhooks**: signatures, and what someone holding a captured delivery could do with it.
- **Server-side requests**: every `fetch` the Worker and its objects make, and whether anything a person types reaches a URL or an API path.
- **Abuse of the live connection** by people allowed on it, strangers on public boards included.

## What was found, and fixed

Most severe first.

**Script from a sign-in link** (high). The `/signin` page returned people to `return_to` with `location.replace`, unchecked, so `/signin?return_to=javascript:…` ran script on Tack's origin for anyone signed in who followed it, and `https://evil.example` was an open redirect. The server's own check could also be passed with a tab or newline (`/\t/evil.example`, which browsers read as `//evil.example`). Both now use one check (`safeReturnTo` in `src/shared/returnTo.ts`): a path on this site, with no control characters, spaces or backslashes, that still resolves to this origin.

**No security headers** (high, as defence in depth). Nothing set a CSP, `X-Frame-Options`, `nosniff` or HSTS, so the app could be framed (clickjacking: a push or an invite is a couple of clicks) and any script injection would have had free rein. Now every response has them (`src/server/securityHeaders.ts`): the Worker's from `withSecurityHeaders`, the static assets' from a `_headers` file the build writes. The app's policy allows scripts only from the app itself and the inline theme script by hash, and nothing may frame it. Testing it in the browser found three things the policy had to allow without weakening it: board pages (`/b/*`) come through the Worker for link previews and were getting the API's policy, which loads nothing (they now get the app's, with the hashes of the inline scripts actually on the page, so the dev server's page works as well); modern-screenshot sets a `<base>` to resolve the stylesheet's fonts, so `base-uri` is `'self'` rather than `'none'`; and avatars at `github.com/{login}.png` redirect to the avatars host, which snapshots fetch.

**Anyone could be anyone in presence** (high). Awareness (cursors, the people list, who's following whom, history's attribution) was relayed exactly as each client sent it, so any connection, a signed-out visitor to a public board included, could claim another person's login, name and avatar, rewrite or remove other people's cursors, and send states of any size. The timer's and spotlight's credits ("Kai stopped the timer") also came from the client. Now every awareness update is checked (`src/server/awareness.ts`): signed-in people are who their sign-in says, guests carry no login or picture, a connection can only speak for its own client ids (at most four), and states are at most 32 KB.

**Webhook replays** (medium). Only a delivery's body is signed: its id and event name are headers anyone holding a captured delivery can change. Deliveries were deduplicated by id alone, and installation events not at all, so a replayed body under a new id was processed again, and a replayed body of another event sent as `installation` could have changed what Tack thought was installed. Now deliveries are told apart by the SHA-256 of the signed body as well (the `Repo` keeps both for three days, the `Instance` installation events' for 30), an installation event only counts if its body is one, and comment commands written more than a week ago are ignored (`stale`). Older payloads never overwrite newer card data anyway, and rules never place an item twice, so a replay past those windows changes nothing.

**API paths from the document** (medium). Card keys come from the document, which any editor writes, and their repository part went into API paths (`/repos/{owner}/{repo}/…`) requested with the viewer's token or the app's. A name with `..` or `?` could have pointed one of those requests at another endpoint. Repository paths must now be plain segments (`isRepoPath` in `src/shared/refs.ts`; `parseKey` and `parseRepoKey` refuse anything else), and the GitHub adapter's own pattern refuses `.` and `..`. Other user-supplied parts of paths (branches, folders) were already encoded segment by segment.

**The app's JWT could follow a link** (medium). The redelivery cron followed GitHub's `Link` header for pagination wherever it pointed, with the app's JWT. It now only follows links to GitHub's API.

**Cross-site checks were per route** (medium). Most routes that change state checked `Origin`, but not all did, and live connections didn't at all (SameSite=Lax keeps the session cookie off cross-site WebSocket handshakes in today's browsers, but that's the browser's choice). Now the Worker turns away every state change and every live connection from another site before any route sees it; webhooks, which are signed, are the one exception.

**`javascript:` links** (medium). Links that come from the document (a comment command's provenance link, an action item's issue link, a push result's URL, a credit's board URL) and from the forge (cards, CI checks, whatever app posted them, releases, pushes' items) were rendered as `href` as they were. They all go through `safeUrl` now, which keeps only http(s); `window.open` for cards too.

**Strangers saw who's on a public board** (low). `GET /api/boards/:id/members` answered signed-out visitors to public boards with every member and invite. They now need to sign in. They still get the members as people who can be mentioned (`/people`), to show mentions in comments by name, as #56 decided, but not recent visitors.

**Presence could fill a board's memory** (low). A connection could invent thousands of presence clients, each a 32 KB state, and the board's object kept them all. Past four per connection, new ones are dropped.

**Imports were read before they were allowed** (low). `POST /api/boards/import` parsed up to 4 MB of JSON before checking the person may make boards. It checks first now.

**Rate limits were handled differently everywhere** (reliability, and how well Tack behaves towards GitHub). Each adapter read GitHub's limits its own way; polling took any error's reset header as a reason to wait; comment command replies didn't wait at all; and once GitHub said a token was limited, other code kept calling with it. Now every GitHub call goes through `forgeFetch` (`src/server/forges/rateLimit.ts`), which notes primary and secondary limits per token (hashed) and resource, answers for GitHub while one holds, and escalates repeated secondary limits; everything reads limits the same way (`rateLimitOf`) and waits for the same `retryAt`.

## Checked, and fine

- **Sessions**: a random id in a signed, `HttpOnly`, `SameSite=Lax` cookie (`Secure` over HTTPS); only its hash is stored, and sign-in makes a new one. GitHub tokens are encrypted at rest with keys derived from `TACK_SECRET`, refreshed with rotation, and never sent to the browser. OAuth uses state and PKCE. Dev sign-in is only declared in development and only answers on loopback hosts.
- **Rendering**: React escapes everything, and nothing renders HTML from content (the one `innerHTML` is a fixed placeholder in snapshots). Markdown previews build React elements and keep only http(s) links and images. The embed renderer draws text as paths (Satori), and link preview tags escape what they carry. Comment command replies defuse mentions, links and Markdown in what they quote.
- **Server-side requests**: the Worker and its objects only call forge APIs at fixed hosts (`api.github.com`, `github.com` for OAuth) and its own objects. Other forges (#65) add the hosts an admin configures in `TACK_FORGES` (and the defaults, `gitlab.com`, `codeberg.org` and `tangled.org` with `api.tangled.org` and `plc.directory`), never one named in a board: a key's host must be one of them, and Forgejo and Tangled keys are only ever `owner/name`, GitLab's project path one encoded segment. At the review, nothing fetched a URL someone typed: embeds draw from the board's data with bundled fonts and no images, and snapshots are uploaded, never fetched. Link cards, added since, are the one exception, behind their own guard: see "Link cards" below.
- **Board data**: per-viewer card filtering, the redacted push log, public boards' anonymous view (`test/public-boards.test.ts`), silent mode's text never in the document, history or anyone else's messages (`test/facilitation-board.test.ts`, `test/history-board.test.ts`), and embeds only for public boards were all re-checked and hold.
- **AI** (#64, added after the review): `POST /api/boards/:id/ai` is for editors (a row in the table), budgeted per board and person, and writes nothing. What the model reads is built on the server from the document and the cards the asker may read: never face-down text, never cards (or repository names) from repositories they can't read, nor, on a public board, anything that isn't public (`test/ai-board.test.ts` searches everything the fake model was sent). Board content is fenced as untrusted in the prompt; whatever the model answers is checked (a widget against its kind's schema, drafts as plain text, rendered by React) and only ever shown to the asker to place as their own edit. Prompt injection from board content can at worst skew a draft its reader then edits.
- **Viewers' writes**: y-partyserver drops document updates from read-only connections, and every custom message that changes something checks the role (the table).

## What's left

- **Editors are trusted with the whole document.** Anyone who can edit can write any key in it, including ones the server usually writes: push statuses (cosmetic: SQLite decides what's pushed), the timer, a vote's state (`VoteGuard` puts wrong ones right), silent marks (`SilentHub.reconcile` does the same) and rules (which only place items from repositories already on the board, with data from deliveries). Making the document enforce per-key permissions would mean filtering Yjs updates by what they touch, which is a large change for people who are already trusted to edit the board.
- **Staged changes are pushed by whoever presses Push**, as them, including changes another editor staged. The push sheet shows every change and who staged it before anything goes, so this is a review step rather than a hole; it's worth knowing on boards with many editors.
- **`style-src 'unsafe-inline'`.** React Flow positions every node with a `style` attribute and snapshots clone the canvas with its styles, so hashes can't cover them. Injected CSS can't run script, and nothing renders HTML from content.
- **Images from any HTTPS host.** `img-src https:` is what lets Markdown previews show images people linked in issue bodies, and avatars from anywhere GitHub serves them. An editor could put a tracking image in a staged issue's body, which loads when someone previews it.
- **The rate-limit gate is per isolate.** Each Worker isolate and Durable Object keeps its own, so a limit one has seen isn't known to the others until they see it too. Every response still carries GitHub's headers, so each learns on its first call; sharing it (say, through the `Instance`) would cost a round trip on every GitHub call.
- **Custom messages from people on a board aren't rate limited** beyond comments (per connection) and widget refreshes and rechecks (throttled). A connection can send `since-request` or `clock` as fast as it likes, but that only costs its own board's object, which is what it's connected to anyway.
- **The session cookie isn't `__Host-` prefixed.** It's host-only already (no `Domain`), so the prefix would add little, and renaming it would sign everyone out.
- **Backups to a public repository** of a board that isn't public are allowed, with a warning in the dialog; cards from other repositories that aren't public are left out of every backup, as are face-down stickies. The owner chooses where their board goes.

## Link cards

Link cards (src/shared/links.ts, src/server/links/) show any web page as its Open Graph preview, so the instance fetches addresses people typed: the one place it does. The threat is server-side request forgery (making the Worker, or a self-hosted runtime, reach something only it can: cloud metadata, a router, a database, `localhost`), using the instance to hammer a site, and leaking who's looking at a board.

**What stops it.**

- **Every fetch goes through `guardedFetch`** (`src/server/links/guard.ts`): http(s) only, standard ports only (the URL parser drops a default port, so any port left is refused), no credentials in the address, and no hosts that only mean something locally (`localhost`, `.local`, `.internal`, `.home.arpa`, single labels…). IP literals are checked after the URL parser has normalised them (`0x7f.1`, `2130706433` and the like are dotted by then) against every range that isn't the public internet, IPv4 and IPv6, including IPv4 inside IPv6 (mapped, translated, NAT64, 6to4), Teredo, ULA (AWS's metadata), link-local (everyone else's), multicast and documentation.
- **DNS first.** Names are resolved over DNS over HTTPS (Workers have no resolver of their own) and refused if any A or AAAA answer is private, so a name pointing at `127.0.0.1` or with one private answer among public ones goes nowhere. This doesn't rely on the fetch resolving the same way: on Cloudflare a Worker's `fetch` can't reach private networks at all, so a rebinding race gains nothing there; the check is what keeps `vp dev` and other runtimes safe.
- **Redirects by hand**, at most three, each hop checked from the start (scheme, port, host, DNS), so a public page can't bounce the fetch somewhere private.
- **Bounded work**: 5 s a hop, 8 s in all, the first 512 KB of a page read and the rest cancelled, images at most 5 MB (SVG 256 KB). Pages are parsed by plain string scanning of the head (no DOM, no scripts), with every field clamped and every address resolved and kept only if it's http(s) (`parsePage`, `readPreview`).
- **Who can make it fetch**: reading a page is for signed-in editors of the board (a row in the access table), rate limited per person and per board, and cached by address for a day, so a board pasted full of addresses, or many boards with the same one, costs little. The image proxy only fetches images a link card on that board shows (`Board.showsLinkAsset`), so it's never an open proxy, even for strangers on a public board; it's rate limited per board and cached for a week.
- **What comes back**: images are typed by their first bytes, never the server's header, and anything that isn't PNG, JPEG, GIF, WebP, AVIF, ICO or SVG isn't passed on; they're served with `nosniff`, `Content-Disposition: inline` and `default-src 'none'; style-src 'unsafe-inline'; sandbox`, so an SVG opened on its own runs nothing and reaches nothing. Previews are text, rendered by React. Links open through `safeUrl` with `rel="noreferrer noopener"`.
- **Privacy**: browsers only ever load images from the app's own origin (`/api/boards/:id/links/image`), so the sites never see viewers' addresses, and the app's CSP needn't trust them. Logs carry the host, never the whole address (a query string may hold something private).
- **The public demo and the playground** never call it: their link service (`src/client/play/links.ts`) answers from canned pages drawn in the browser, and the demo's policy allows no images from elsewhere anyway (`e2e/try.spec.ts` checks no request goes out).

**What's left.**

- **The rate limits are per isolate**, as the client error reports' are: several isolates each allow their own budget. Caching keeps the cost of a repeat low; a shared counter would cost a round trip on every unfurl.
- **A page knows it was read.** Its server sees the Worker's request (`TackLinkPreview/1.0`), so pasting a link with a secret token in it tells that site the link was opened, once a day at most. That's true of any chat app's link previews too.
- **Previews are the board's content.** Whatever a page says about itself is written into the board for everyone who can open it, like a sticky's words, so a page could say something misleading. It's text, never markup.
- **No resizing.** Images are passed on at their own size (up to 5 MB); resizing would need the Images binding, which not every instance has.

## Custom widgets (#66)

Custom widgets run code that people who can edit a board wrote, in every browser that opens the board, reading data as whoever's looking. That's the most powerful thing an editor can do in Tack, so it's off on every board until its owner turns it on (`board_settings` in the Directory; `PATCH /api/boards/:id` with `customWidgets`, owners only), with a warning that says what it means before it's on. This is the threat model.

**Who's trusted.** The board's owner decides; its editors write the code; everyone who opens the board runs it. The code is untrusted: we assume an editor could be malicious, or have pasted something they didn't read.

**What it could want.** Data the viewer can read and the editor can't (private repositories, `@me` searches, cards on the board); the viewer's session or GitHub token; acting as the viewer (pushing, inviting, commenting); tricking the viewer (phishing, clickjacking); or just breaking the board (freezing it, flooding GitHub).

**What stops it.**

- **An opaque origin.** The iframe has `sandbox="allow-scripts"` and nothing else, and the page it loads (`GET /sandbox/widget`, `src/server/widgets/sandbox.ts`) sandboxes itself in its CSP too, so it's the same even opened on its own. Without `allow-same-origin` it has no cookies, storage, or access to Tack's DOM, and Tack's session cookie never reaches it. Without the other flags it can't open windows, navigate the top frame, submit forms, show modals, lock the pointer or download.
- **No network.** The page's policy is `default-src 'none'` with `connect-src 'none'`, images, fonts and media only from `data:`/`blob:`, no frames, workers, objects, forms, manifests or `<base>`. Scripts are inline only: the bootstrap, and the widget's code it adds. WebRTC isn't covered by CSP, so the bootstrap removes its constructors before the code runs (and a fresh frame of its own doesn't give them back: `e2e/custom-widgets.spec.ts` checks that with the sandbox check widget, along with fetch, images, WebSockets, cookies, storage, the parent's DOM and popups).
- **Navigation.** A sandboxed frame can still navigate itself. The app's own CSP (`frame-src 'self'`) stops it going anywhere but Tack, and everything Tack serves but the sandbox page sends `X-Frame-Options: DENY`, so the most it can do is break itself (the board then stops it). The e2e test checks this on a real board under the app's policy.
- **A narrow, read-only API.** The frame only talks to the board by `postMessage`. The board (`SandboxHost`, `src/client/widgets/custom/sandbox.ts`) only listens to its own frame's window (`event.source`), checks every message's shape and sizes (`parseFrameMessage`), and answers three requests: searches, which go to the server as the widget's searches (`widget-query`) and run through the widget runner with the viewer's own access (so they see exactly what that viewer could, and strangers on public boards only public data); cards the board has already sent this viewer; and avatars from `avatars.githubusercontent.com` only, which the app fetches without credentials and hands over as `data:` URLs. Nothing in the API writes: no staging, pushing, comments or document changes. Responses only go to the frame's window.
- **The server enforces the switch.** Each connection carries whether custom widgets are on; the runner only takes `widget-query` for shapes that are custom widgets, at most eight searches each and fifty widgets per connection, each checked like any widget's query (`customQueryOf`), and answers them as off while the owner has them off. Turning them off forgets every connection's custom searches at once.
- **Limits.** Per widget: 120 requests a minute, 8 in flight, 20 seconds each, 64 avatars; searches are cached, budgeted and refreshed like other widgets', so a widget can't make Tack hammer GitHub. Code and settings are capped (64 KB and 8 KB), as are log lines.
- **Freezing.** In Safari and Firefox (and in Chrome, for all of a page's sandboxes together) the frame shares a thread with something else, so a loop that never ends would hang the board, and a ping can't interrupt it. Before the code runs, every loop gets a check at the top of its body (`guardLoops`, with acorn); a loop that keeps the thread for more than a second without a task getting to run throws, naming its line. Where the frame is in its own process (Chrome, mostly), a frame that stops answering pings for six seconds is removed.

**What's left.**

- **A widget sees what its viewer sees, and side channels exist.** Browsers have ways out no policy closes completely: DNS prefetching in some browsers (the page sets `X-DNS-Prefetch-Control: off`, which not every browser honours), timing, and whatever a future browser feature adds before CSP covers it. A determined editor might get a little data out this way. That's the reason for the owner's switch, off by default, and the warning: turn it on only where you trust everyone who can edit.
- **Editors can change the code after the owner turned them on.** The switch is per board, not per widget or per version of the code; there's no review step. A per-widget approval (the owner approving a hash of the code) would close this; it's a reasonable next step if boards with many editors want custom widgets.
- **Hangs other than loops.** The loop guard catches loops, not a regular expression that backtracks forever or a huge allocation. Where the sandbox shares the board's thread, those can still freeze the tab; reloading and asking the owner to turn custom widgets off (or removing the widget from another tab before it loads) recovers.
- **Clickjacking inside the widget.** A widget draws whatever it likes in its own rectangle, which could look like part of Tack. It can't act on anything outside, so the worst is a misleading picture; it's labelled "Custom · runs in a sandbox" with a "Sandboxed" footer.
